Git keeps several optional files next to its objects that make large repositories fast. None of them
hold new information; each is a cache of something Git could compute from objects, and Git falls
back to computing it when the file is missing. This page also covers serving transfers and Git's
standalone tools.

## commit-graph

`.git/objects/info/commit-graph` indexes a set of commits by parents, root tree, commit date and
**generation number** in a compact indexed table. Without it, each step of a
[history walk](/girt/how-git-works/config-and-revisions/#history-walks) finds, decompresses and
parses a commit object; with it, a step is an array lookup.

A commit's generation number is one more than its parents' highest. A commit can't be an ancestor of
a commit with a lower or equal generation, so walks can stop as soon as they pass below the target's
generation instead of visiting the whole excluded history. Newer files can also store corrected
commit dates: the greater of the commit's date and one more than every parent's corrected date.
These remain ordered even when commit clocks disagree.

Optional **changed-path Bloom filters** can rule out changes to a path relative to the first parent.
A positive answer can be a false positive and requires comparison; merge filters do not rule out
differences from other parents. Git writes a standalone graph during `git gc` by default unless
`gc.writeCommitGraph` disables it. Default `git maintenance run` writes split chains, as does its
explicit commit-graph task. Reading an existing graph is enough to benefit. Girt attaches valid
graphs to repository object readers by default, honoring `core.commitGraph=false`; unusable graphs
fall back to object reads, and object verification is available explicitly. Like Git, default
opening checks the graph's structure but not its whole-file checksum, which explicit parsing and
verification still check.

<GirtStatus status="partial" href="https://docs.rs/girt/latest/girt/commit_graph/index.html">Single/split reading and writing, explicit verification, default indexed history and first-parent Bloom queries; opening overhead and automatic GC writing remain. Remaining work is tracked in [#492](https://github.com/joshka/girt/issues/492).</GirtStatus>

On Linux v6.1, reading records in place ([#733](https://github.com/joshka/girt/pull/733)) took a
near-tip ancestry check from 700 ms to 51.6 ms, against 10.5 ms for Git, and counting `v6.0..v6.1`
from 726 ms to 68.5 ms, against 54.6 ms. Peak memory fell from 504 MiB to 107 MiB. About 36 ms of
the remaining near-tip time was the whole-file checksum, which default opening now skips. The
[opening-cost issue](https://github.com/joshka/girt/issues/625) links raw measurements. This is
progress toward Git parity rather than parity.

## Multi-pack index

Repositories collect many [packs](/girt/how-git-works/storage/#packs), roughly one per fetch, and an
object lookup checks each pack's index in turn. A **multi-pack index**
(`.git/objects/pack/multi-pack-index`) is one index across all packs, so a lookup is a single binary
search however many packs there are.

<GirtStatus status="partial" href="https://github.com/joshka/girt/issues/517">Single/incremental reading, standalone writing with bitmaps, and verification; automatic maintenance and existence-path acceleration remain.</GirtStatus>

## Reachability bitmaps

A **reachability bitmap** stores, for selected commits, one bit per object in a pack saying whether
it is reachable from that commit. "Which objects does this client need?" becomes bitwise operations
(reachable from the wants, minus reachable from the haves) instead of a graph walk. Bitmaps make
serving clones and fetches fast, and speed up counting objects and repacking.

<GirtStatus status="partial" href="https://github.com/joshka/girt/issues/518">Pack/MIDX bitmap reading and writing, explicit publication, explicit-only repack configuration, and exact want/have differences; incremental bitmap acceleration, pseudo-merges, query binding reuse and writer performance remain.</GirtStatus>

## fsmonitor and the untracked cache

[Status](/girt/how-git-works/working-tree/#status) checks every tracked file's stat data and scans
every directory for untracked files. On a monorepo that takes seconds. **fsmonitor**
(`core.fsmonitor=true`) asks a file-watcher daemon which paths changed since the last query, so Git
only checks those. The **untracked cache** (`core.untrackedCache`), an index extension, remembers
directory listings so finding new files doesn't rescan unchanged directories. Together they make
status take milliseconds.

<GirtStatus status="partial" href="https://github.com/joshka/girt/issues/519">Configured status reuses valid UNTR listings under exact byte name policy. Explicit opt-in hook queries (protocols 1 and 2) can skip tracked stat calls using FSMN checkpoints. Explicit cache refresh uses the index lock and atomic publisher; built-in daemon IPC is explicitly refused.</GirtStatus>

## Serving

The server side of [transfer](/girt/how-git-works/transfer/) runs `git-upload-pack` for fetch and
clone and `git-receive-pack` for push: advertise refs, negotiate, build a pack, or receive one and
apply ref updates. A Rust forge, a jj server or self-contained test fixtures need this.

<GirtStatus status="partial" href="https://github.com/joshka/girt/issues/520">Serves protocol v2
`ls-refs` and `fetch` to Git clients, including shallow clones and hidden refs, through
`girt upload-pack`, in protocol v2 and v0. Filters and receive-pack are not served yet.</GirtStatus>

## Partial clone

`git clone --filter=blob:none` downloads every commit and tree but no file contents. The repository
records the remote as a **promisor**, and any later read of a missing blob fetches it on demand.
Large repositories clone in a fraction of the time. Everything that reads objects has to know a
missing object may be promised rather than lost.

## Bundles

A **bundle** (`git bundle create repo.bundle --all`) is one file holding a pack plus a list of refs:
a portable snapshot of some or all of a repository. You can clone or fetch from it like a remote. It
is used to move repositories without a network and for **bundle URIs**, where a server points
clients at a prebuilt bundle on a CDN to download first, then fetches the rest.

<GirtStatus status="partial" href="https://github.com/joshka/girt/issues/523">Library support reads v2/v3 bundles, verifies and creates full/incremental bundles, and receives through fetch/clone publication. CLI commands, revision-range and automatic file-source integration remain; bundle URIs and filtered promisor installation are follow-ups.</GirtStatus>

## fsck

`git fsck` checks a repository's integrity: every object parses and hashes to its ID, every ref
points at an existing object, and every object reachable from a ref is present. It also reports
unreachable ("dangling") objects.

<GirtStatus status="partial" href="https://github.com/joshka/girt/issues/828">Whole-repository object/connectivity checks, unreachable/dangling reporting, pack and auxiliary-index verification, configured severity/skip-list policy, CLI reporting and lost-found export. Commit/tag header and identity diagnostics match Git fixtures; configured fetch/clone and local receive enforce payload policy before installation. Further reference and metadata-blob emitters remain.</GirtStatus>

## grep

`git grep` searches file contents in the working tree, the index, or any commit's tree, limited by
pathspecs. By default it searches tracked files, including tracked files that match `.gitignore`;
[ignore rules](/girt/how-git-works/working-tree/#ignore-rules) only matter with `--untracked`, which
then hides tracked files that match them too. Searching a commit reads blobs straight from the
object database, without a checkout.

<GirtStatus status="partial" href="https://github.com/joshka/girt/issues/525">Searches the working tree, the index, trees and plain directories with `git grep`'s output; no `-P`, `--textconv` or submodules.</GirtStatus>

## archive

`git archive --format=tar v1.0` exports a tree as a tar or zip file, leaving out paths with the
`export-ignore` [attribute](/girt/how-git-works/other/#attributes). Release tooling uses it to build
source tarballs.

<GirtStatus status="partial" href="https://github.com/joshka/girt/issues/526">Writes tar byte for byte as Git does, plus tar.gz and zip, with `export-ignore`, `export-subst` and content filters; some `export-subst` placeholders are refused.</GirtStatus>

## bisect

`git bisect` binary-searches history for the commit that introduced a bug. You mark one commit good
and one bad; Git checks out a commit halfway between, you test it and mark it, and after about
log₂(n) steps it names the first bad commit. It is mostly history-walk logic plus a little state in
`.git/BISECT_*` files.

<GirtStatus status="supported" href="https://github.com/joshka/girt/issues/527">`girt::bisect` shares Git's state files and picks the commits Git picks, skips included.</GirtStatus>

## rerere

**rerere** ("reuse recorded resolution", `rerere.enabled=true`) records how you resolved a
[merge conflict](/girt/how-git-works/combining-work/#merging) under `.git/rr-cache/` and resolves
the same conflict automatically next time, which helps when rebasing a long-lived branch repeatedly.

<GirtStatus status="supported" href="https://github.com/joshka/girt/issues/528">`girt::rerere` and `girt rerere` share Git's `rr-cache`; callers run it after publishing a conflicted merge.</GirtStatus>

## Replace refs and grafts

A ref `refs/replace/<id>` makes Git transparently use another object wherever `<id>` is read, for
example to stitch an imported old history onto a newer one. Grafts (`.git/info/grafts`) are the
older, deprecated form. Where they are used, a tool that ignores them shows different history from
Git.

<GirtStatus status="partial" href="https://github.com/joshka/girt/issues/529">Reading through replace refs and grafts is opt-in, and raw object reads never substitute. Converting a grafts file to replace refs is not supported yet.</GirtStatus>

## Hooks

**Hooks** are programs Git runs at set points: `pre-commit` and `commit-msg` before a commit,
`post-checkout` after checkout, `pre-push` before a push. They live in `.git/hooks/` or the
directory in `core.hooksPath`, and a non-zero exit from a `pre-` hook stops the operation. Tools
that commit or push on a user's behalf may need to run a repository's hooks the way Git does.

<GirtStatus status="partial" href="https://github.com/joshka/girt/issues/530">Hooks run only when a caller opts in, on Linux and macOS. Commit runs its four hooks, switch runs `post-checkout` and push runs `pre-push`; a native local push runs the receiving repository's hooks. Other hooks, such as `reference-transaction`, `post-merge` and `post-rewrite`, are not run.</GirtStatus>

## Automatic maintenance

`git gc --auto` runs after many commands and repacks when there are more than `gc.auto` loose
objects (6700 by default) or `gc.autoPackLimit` packs (50). `git maintenance` schedules tasks such
as writing the commit-graph, prefetching and incremental repacking. Both decide when the individual
operations ([repacking](/girt/how-git-works/storage/#repacking-and-pruning), packing refs, pruning)
should run.

<GirtStatus status="partial" href="https://github.com/joshka/girt/issues/531">Callers can explicitly check `gc.auto` and `gc.autoPackLimit` to learn whether housekeeping is due. The check starts no background work; task execution and pruning policy remain caller-controlled.</GirtStatus>
