<CliNotice />

References are the names that point into the object graph: branches, tags, remote-tracking branches
and `HEAD`. `girt ref` reads them from whichever backend the repository uses, loose files with a
`packed-refs` file or reftables, and changes them only through checked transactions. The library
side is in [Read and update refs](/girt/guides/refs/).

## List references (`girt ref list`)

<Example cmd="ref list">

`girt ref list` prints `<id> <name>` for every reference, sorted by name. Give one or more prefixes
to narrow the list; `--symbolic` shows only symbolic references, with `-> <target>` appended.

```console
$ girt ref list
7ed7a0cc68995713f52d973e6adfd3d9e667324f refs/heads/main
90772130c5df4563a3c4c46956d4120724dfed1a refs/heads/topic
2e689a32bdb3c8620a41217104519c8fac9d029e refs/tags/v0.1
$ girt ref list refs/heads
7ed7a0cc68995713f52d973e6adfd3d9e667324f refs/heads/main
90772130c5df4563a3c4c46956d4120724dfed1a refs/heads/topic
```

</Example>

## Resolve a name (`girt ref show`)

<Example cmd="ref show">

`girt ref show` expands a short name the way Git does and prints each hop of a symbolic chain,
ending at the object ID. It is a quick way to see what `HEAD` means in a repository.

```console
$ girt ref show HEAD
HEAD -> refs/heads/main
refs/heads/main -> 7ed7a0cc68995713f52d973e6adfd3d9e667324f
```

</Example>

## Move a reference safely (`girt ref set`)

<Example cmd="ref set">

`girt ref set <name> <revision>` points a reference at an object. Pass the full ID you last saw with
`--expect` and the update happens only if the reference still has that value; `--create-only`
refuses to overwrite an existing reference. Either way a concurrent writer can't be silently
overwritten.

```console
$ girt ref set refs/heads/release main~1 --create-only -m "start release"
$ girt ref set refs/heads/release main \
    --expect 3dc25d2e2eeed699cba1e1ea0314dd88299f9b02 -m "advance release"
$ girt ref set refs/heads/release main~1 \
    --expect 3dc25d2e2eeed699cba1e1ea0314dd88299f9b02
Error:
   0: updating refs/heads/release
   1: reference transaction preparation failed
   2: reference value did not match the expected value (found 7ed7a0cc68995713f52d973e6adfd3d9e667324f)
```

The third command fails because the second already moved `release`: the ID it expected is stale.
`ref set` also refuses an object that doesn't exist, and anything but a commit when the reference,
after following symbolic references, is a branch.
`girt ref log release` now shows both updates:

```console
$ girt ref log release
7ed7a0cc68995713f52d973e6adfd3d9e667324f 3dc25d2e2eeed699cba1e1ea0314dd88299f9b02 advance release
3dc25d2e2eeed699cba1e1ea0314dd88299f9b02 0000000000000000000000000000000000000000 start release
```

</Example>

Setting a symbolic reference such as `HEAD` updates the branch it points at. When
`core.logAllRefUpdates` says the reference is logged, girt appends a reflog entry with `-m`'s
message and the committer from `user.name` and `user.email` (or `GIT_COMMITTER_NAME` and
`GIT_COMMITTER_EMAIL`). The entry's time is in UTC; girt doesn't read the local time zone.

## Delete a reference (`girt ref delete`)

<Example cmd="ref delete">

`girt ref delete` removes a reference and its reflog. `--expect` makes the deletion conditional on
the current value, as with `ref set`.

```console
$ girt ref delete refs/heads/release --expect 7ed7a0cc68995713f52d973e6adfd3d9e667324f
$ girt ref list refs/heads
7ed7a0cc68995713f52d973e6adfd3d9e667324f refs/heads/main
90772130c5df4563a3c4c46956d4120724dfed1a refs/heads/topic
```

</Example>

## Read a reflog (`girt ref log`)

<Example cmd="ref log">

`girt ref log` prints a reference's reflog newest first, as `<new-id> <old-id> <message>`.

```console
$ girt ref log main
7ed7a0cc68995713f52d973e6adfd3d9e667324f 3dc25d2e2eeed699cba1e1ea0314dd88299f9b02 commit: Ignore target
3dc25d2e2eeed699cba1e1ea0314dd88299f9b02 e896f1ed22a211bd58c4b542fba2323ad09a52b0 commit: Add a second line
e896f1ed22a211bd58c4b542fba2323ad09a52b0 0000000000000000000000000000000000000000 commit (initial): Initial commit
```

</Example>

With `--git` it prints Git's `<abbrev> main@{N}: <message>` form, with abbreviations as long as
`core.abbrev` and the repository's size require.

## Replace an object (`girt replace`)

<Example cmd="replace graft">

A replace reference, `refs/replace/<id>`, makes `girt log`, `girt history` and `girt object` read
another object wherever `<id>` is read, as Git does. Stored objects and IDs don't change.
`girt replace graft <commit> <parent>...` stores a copy of the commit with new parents and points
the replace reference at it. Here the root of a new history is stitched onto an imported old one:

```console
$ girt log --oneline --git
17b5858 Add feature
d08138f Start new history
$ girt replace graft new~1 old
c8d4ca296c2753f9c88242b66181eaf130c4804c
$ girt log --oneline --git
17b5858 Add feature
d08138f Start new history
d752ff1 Import old history
$ girt replace list
d08138fbe341633b0912179cc92d9df398f315aa c8d4ca296c2753f9c88242b66181eaf130c4804c
```

</Example>

The global `--no-replace-objects` reads stored objects as they are, as do
`core.useReplaceRefs=false` and `GIT_NO_REPLACE_OBJECTS`.
`girt replace set <original> <replacement>` replaces one object with another of the same kind
(`--force` allows another kind or overwrites an existing reference), and
`girt replace delete <object>` removes the reference. Grafts in `.git/info/grafts`, the older form,
are read too. In the library, reads substitute only through `ReplacedObjects`
([#529](https://github.com/joshka/girt/issues/529)).
