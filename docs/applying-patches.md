# Apply patches in memory

Use `girt::apply` when an application owns file contents and needs to apply a unified diff without
opening a working tree. Parse the complete patch, select a file edit, and pass its preimage bytes:

```rust
use girt::apply::Patch;

let patch = Patch::parse(b"--- a/name\n+++ b/name\n@@ -1 +1 @@\n-old\n+new\n")?;
let applied = patch.files()[0].apply(b"old\n")?;
assert_eq!(applied.content, b"new\n");
# Ok::<(), girt::apply::Error>(())
```

`Applied` owns the complete postimage and reports each applied hunk's patch line and zero-based
preimage/postimage positions. A failure returns no partial content. The caller decides whether and
how to publish the bytes; this API reads and writes no objects, index entries or working files.

Paths remain bytes, including the original `a/` and `b/` prefixes. Quoted Git paths are decoded and
traditional tab-separated timestamps are removed. `/dev/null` becomes an absent side. Callers must
check source existence, destination absence and destination-specific path safety themselves. A
successful content application does not authorize opening a path from an untrusted patch.

`Patch::parse_with` and `FilePatch::apply_with` accept `Limits` to bound input bytes, file count,
hunk/content-line counts and postimage bytes. The default byte bounds are 16 MiB, with at most
100,000 content-line allocations. Parsing and exact-position matching take work proportional to
input and output size; there is no offset search. File edits remain in input order and duplicate
paths are retained for the caller to interpret.

## Supported scope

The initial API applies unified text replacements, insertions and deletions at their declared
positions. It preserves CR, non-UTF-8 bytes and missing final newlines. Context and removed lines
must match exactly, and the declared postimage positions must agree with preceding hunks.
Zero-context hunks are accepted, analogous to opting into Git's `--unidiff-zero`.

Git `diff --git` and `index` lines provide framing and metadata. Text object IDs are syntax-checked
without asserting preimage identity; declared modes are checked during tree application, and binary
object IDs are checked against content. File paths come from `---` and `+++`. Combined diffs and
submodule modes return explicit unsupported errors. Git mode changes, new/deleted files and
rename/copy metadata (including declared similarity) are retained and applied. Offset/fuzz matching,
whitespace options, reverse application, recount, index/worktree publication, format-patch and
mailbox/am remain tracked in
[issue 506](https://github.com/joshka/girt/issues/506).

The parser requires a standalone patch: mail headers, prose and signatures must be removed first.
Empty context lines require their leading space, and missing-newline markers require the English
`\ No newline at end of file` spelling. Reduced trailing context does not pin an exact-position hunk
to EOF as Git's default matching does; a missing-final-newline marker always requires EOF.

## Apply to a stored tree

`Patch::apply_tree(&objects, base)` reads affected directories and blobs and returns an owned
`AppliedTree`. It strips one path component by default (`a/` and `b/`), checks and applies declared
file modes, preserves existing modes otherwise and uses regular-file mode for additions without a
mode and prunes emptied parent directories after deletions. Unrelated subtrees retain their IDs,
including stored empty directories. Git's index cannot retain empty directories, so an index round
trip can normalize those entries away.

Inspect `result.tree()` and `result.files()` before calling
`result.install_objects(&repository.loose_objects())`. Installation writes generated immutable
objects in dependency order; it changes no refs, index or working files. On storage failure, some
additive objects may remain. Publishing the resulting root also requires retaining the unchanged
objects from the source store; installing generated objects into another repository does not copy
that dependency closure.

`apply_tree_with` accepts `TreeOptions` for component stripping and a directory prefix, and
`TreeLimits` for directory reads, entries, path bytes, depth and aggregate generated bytes. It also
takes a cancellation flag. Duplicate destinations, repeated non-copy sources, differing names
without rename/copy metadata, existing addition destinations, missing sources, directory
replacements and traversal through leaves are refused. Rename cycles read original preimages; copies
retain their source. All paths remain repository-relative bytes; these checks do not authorize
filesystem publication.

Tree application refuses `.git` path components in any ASCII case. Filesystem-specific aliases still
require the publication destination's checks. Sources are read before path edits; replacing a
directory emptied by other edits in the same patch is currently refused, although Git can apply that
transition. The path-byte budget counts old and new mapped sides separately, even when equal, plus
every newly visited directory path.

## Binary patches

Git `GIT binary patch` records are decoded from base85 and zlib into literal bytes or pack-delta
instructions. `FilePatch::binary_kind()` identifies the forward encoding; a second block is retained
and its encoding can be inspected with `reverse_binary_kind()`, but reverse application is not yet
exposed. Both records count against `Limits::max_binary_bytes`, an aggregate inflated-payload bound
across the whole patch. The existing output bound separately caps a reconstructed delta result.

Binary application requires full same-format `index` identities and checks the supplied preimage and
computed postimage hashes. A new or deleted side uses Git's null identity. Tree application also
checks that the patch's hash format agrees with storage. Malformed base85, zlib framing and size
declarations fail during parsing; delta instructions and result identity are checked when applying
against a preimage. Binary diff summaries without encoded content remain unsupported.

The extended parser currently expects default `a/` and `b/` prefixes for rename/copy metadata;
non-default and omitted prefixes can be refused before path mapping. Dissimilarity headers from
Git's break-rewrite output are explicitly unsupported. Binary blocks require their terminating blank
line, including the final block.
