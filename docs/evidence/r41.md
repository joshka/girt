# R41 Representative Performance Checkpoint

R41 improves normal packed reads and keeps the A20 Git-parity target open. On the retained macOS
SHA-1 fixture, buffered girt throughput rises from 0.20–0.23x Git to 0.43–0.48x for ordinary blobs.
Selected deep deltas rise from 0.016–0.023x to 0.038–0.053x. The gains are substantial, but neither
range establishes parity. The [external report](/Users/joshka/.codex/reports/girt-r41/README.md)
retains the generated fixtures, harness, raw Criterion samples, logs, memory observations, and
profiling output. The older [R15 report](/Users/joshka/.codex/reports/girt-vs-git/README.md) remains
a separate fixed-snapshot comparison, not the before row below.

## Scope and Changes

The current-code baseline starts after scoped C02 acceptance at `514c2abc`. Four independent jj
changes improve the same packed-read path:

1. `042828e0` retains validated, bounded index bytes so binary searches and delta identity checks
   avoid repeated index seeks. Each lookup detects a truncated pinned index; pinned handles,
   immutable-artifact requirements, opening checks, and per-read limits remain.
1. `b84e9156` selects flate2's `zlib-rs` backend. This also changes the compressor implementation
   for newly written packs, without changing their Git formats or object identities.
1. `7729646b` inflates directly into the bounded result buffer. An extra byte detects overflow; the
   8 KiB decode and cancellation cadence remains.
1. `4777da01` uses `aws-lc-rs` for SHA-1 and SHA-256 object and pack hashes. Identity checks still
   cover every base and intermediate delta. Its prebuilt NASM feature supports Windows builders
   without NASM; native validation covers that path. The dependency's native build cost remains a
   tradeoff. The `aws-lc-rs`/`aws-lc-sys` and `zlib-rs` licenses were checked in their package
   manifests; they are permissive ISC/Apache/MIT/BSD and Zlib terms, respectively.

No public API changed. Object payloads remain owned, no decoded-object cache is added, and opening
still checks the whole pack/index snapshot before serving reads. The retained index input adds up to
`PackLimits::max_index_bytes` across packs (64 MiB by default), inside the existing fourfold
input/derived-table allocation bound. The fixture index is 10,256 bytes. Each pair still pins two
handles. Decode output allocates its declared bounded size at the start of inflation, including when
a corrupt stream later proves short; this changes peak timing, not the bound.

## Paired Packed-Read Measurements

The table gives **girt/Git throughput ratios** for matched buffered persistent `cat-file` protocols.
Each range spans the medians of two complete 20-sample Criterion passes, with Git and girt order
reversed. The direct library observation has no matching Git library boundary and is reported
separately in the external report. Times and confidence intervals are retained in each stage's
`medians.csv` and `criterion-run-*` directories.

| SHA-1 workload          | Baseline ratio | Final ratio  |
| ----------------------- | -------------- | ------------ |
| 128 B packed, one ID    | 0.199–0.208x   | 0.442–0.449x |
| 128 B packed, 64 IDs    | 0.204–0.206x   | 0.466–0.479x |
| 1 MiB packed, one ID    | 0.223–0.225x   | 0.430–0.438x |
| 1 MiB packed, eight IDs | 0.212–0.229x   | 0.426–0.449x |
| 64 KiB, depth 14        | 0.016x         | 0.038–0.039x |
| 64 KiB, depths 7–14     | 0.022–0.023x   | 0.051–0.053x |

Git's same-run denominator also varies; ratio gains should not be read as exact CPU speedups. Direct
girt reads improve from 10.5–11.5 to 4.45–4.61 microseconds per small object, 1.17–1.29 ms to
0.51–0.55 ms per 1 MiB object, and 0.99–1.13 ms to 0.44–0.45 ms per repeated depth-14 object. The
warm eager `Repository::objects` open/validate median falls from 9.31–9.54 to 4.26–4.28 ms; that
operation has no equal-work Git baseline. Single-shot small-object service, including startup,
opening, transfer and shutdown, falls from 11.68–12.18 to 6.60–6.64 ms, versus Git's 5.01–5.07 ms.

The second fixture adds SHA-1 and SHA-256 packed blobs and trees plus 32 varied loose 4 KiB blobs
per format. It uses one 20-sample pass and the same owned-output buffered protocol. Its final
girt/Git ratios are 0.40x/0.37x/2.24x for SHA-1 packed blob/tree/loose reads, and 0.38x/0.38x/2.22x
for SHA-256. The pre-hash-change SHA-256 packed blob/tree ratios were 0.19x/0.27x, with loose reads
at 1.52x. Exact bytes from both engines and direct girt reads matched before measurement. These are
object-service observations; they do not yet measure reference resolution, writes, traversal, or
whole jj workflows against matched Git operations.

As one-pass girt-only sentinels using existing Criterion benches, warm HEAD resolution takes a 39.1
microsecond median, a packed reference read from 10,000 entries takes 3.00 ms, bare repository
opening takes 87.4 microseconds, and parsing a 1,024-entry tree takes 38.9 microseconds. Their
fixtures and operation boundaries differ from Git commands, so they carry no A20 parity ratio.

## Attribution, Resources, and Limits

The index-only stage substantially reduces small direct-read time but barely moves deep-delta time.
The zlib switch improves small reads again, with little large/delta effect. Direct output removes a
copy and improves ordinary reads by about 5%. An independent five-second `sample` of the repeated
deep-delta adapter before the hash switch places 3,495 of 3,810 active stack samples in the software
SHA-1 compression routine. This is sampling evidence, not a precise cost allocation. `ring` was
tested and abandoned after its first pass increased the deep direct batch from about 32 to 69 ms and
the large direct batch from about 8.8 to 18.4 ms. The `aws-lc-rs` trial instead reduced the deep and
large batches, and exact Git fixture bytes remained equal. A final five-second sample still places
3,101 of 3,786 active stacks in the accelerated SHA-1 block routine, explaining why repeated deep
chains retain a large gap without attributing a precise share of wall time. The external report
retains both trials.

Fresh-process `/usr/bin/time -l` RSS observations for varied batches are single samples, not
statistical bounds. Baseline/final girt peaks are 2.28/2.36 MiB for small blobs, 3.20/3.19 MiB for
large blobs, and 3.03/2.91 MiB for deltas. The corresponding Git peaks are about 7.3, 16.3 and 11.8
MiB. These measurements exclude retained consumer payloads and do not resolve small memory
differences from desktop noise. Aggregate index bytes and pinned handles remain bounded by
`PackLimits`; each read remains bounded by `ReadLimits`. No cache or negative lookup state exists.

These are warm filesystem-cache measurements on one Apple M2 Max with Git 2.55.0 and Rust 1.98.1,
using default optimized release settings. The original R15 generator creates 328 independent and
related blobs; the added fixture generator creates original SHA-1/SHA-256 objects through Git's
executable. Neither fixture models a large multi-pack store, cold storage, concurrent readers, cache
eviction, writes, transport, traversal or complete jj operation weighting. Git's lazy validation and
girt's eager opening still differ. Repeated/varied sets are finite and fit in RAM; there is no
application object cache in either girt adapter. The first pass of the added cross section is useful
for coverage, not a native-platform distribution or a parity verdict.

## Follow-Up and Acceptance Boundary

R41 is ready for a **scoped** coordinator decision under the roadmap's latency policy. The remaining
ordinary packed gap and especially the selected deep-delta gap belong to
[B05](../jj-roadmap.md#b05--residual-packed-read-performance). R35 should reopen it if a measured
ordinary jj workflow is dominated by packed reads; R34 must reassess the complete representative
corpus before claiming A20 parity. A decoded-object cache or altered validation schedule needs an
explicit memory/ownership budget and first-read versus warm-hit evidence. No cache was introduced to
make these finite repeated batches appear representative of an unbounded repository.

The local library tests, formatting, lint, full development checks and native publication results
are recorded in the external report. Native performance was measured only on macOS; the existing
R15/C02 native correctness evidence is not a cross-platform performance sample. The broad C02
Windows tracing matrix remains failed independently of this performance work.
