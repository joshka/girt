# R28 Fetch Publication Evidence

R28 composes a validated fetch with conditional object, shallow metadata, and reference publication.
The tested implementation revision is `6142e09392c0d0f98ea59381e08abcc745e77755`, published as
`joshka/r28-fetch-publication` on top of the separate R27 scoped-acceptance note. No jj consumer,
push policy, clone checkout, or release state changed.

## Supported Workflow

`FetchRequest` captures destination refs and shallow boundaries before network work, maps the
advertisement from the actual transfer, and keeps the validated response attached to that plan. The
workflow supports positive, negative, exact, wildcard and source-only full-name fetch refspecs.
Missing exact sources are returned in `FetchReport::missing` while valid mappings can continue. Git
2.55.0 instead aborts the corresponding CLI fetch before publishing a valid mapping; the difference
is explicit caller policy. No `FETCH_HEAD` or implicit tag following is performed. Tag destinations
remain caller-selected and replacement requires both `+` and exact name authorization.

Remote-tracking replacements peel both tips and require a fast-forward when both are commits, unless
force syntax and exact name authorization both permit a rewind. Other object-kind replacements are
allowed after validation. Optional pruning deletes only direct remote-tracking destinations owned by
a positive mapping whose source is absent; negative mappings protect their matched sources. Symbolic
remote HEAD aliases, tags and unrelated remotes are not pruned. Every changed destination, including
a prune deletion, uses its captured exact expected value. Unchanged destinations are not rewritten.

Depth requests on v0/v1 streams, HTTP and Unix SSH coordinate shallow metadata with installed
objects. The supplied verified known history must contain all captured shallow boundaries. The
workflow checks a conventional `shallow.lock` and the old boundary snapshot, installs the
self-contained pack, verifies selected tips and old boundaries under the proposed new boundaries,
publishes the shallow file, reopens the repository, and then conditionally publishes refs. Direct
`ReceivedFetch::install` continues to reject shallow results. Native local storage transfer does not
accept a depth request.

## Compatibility and Failure Evidence

Original disposable Git repositories provide SHA-1 and SHA-256 commits, trees, tags and refs.
`tests/fetch_workflow.rs` compares initial and incremental mappings, exclusions, tag and remote
update rules with Git, and tests missing exact refs, scoped pruning, concurrent ref changes, failed
installation, cancellation, corrupt local shadow objects and reference lock failures.
`tests/discovery.rs` drives Git v0 upload-pack for initial depth and deepening in both formats,
checks published shallow boundaries and readable history, and injects a reference lock failure after
successful object and shallow publication. A fresh request recovers that partial state.
`tests/http.rs` and `tests/ssh.rs` exercise the same depth publication path against Git services in
both formats. Existing reference-transaction fault/race cases retain per-ref and reflog
partial-effect evidence.

Object installation can leave an unindexed pack on failure. After successful installation, update
rejection or cancellation leaves installed objects; after shallow replacement, a later reference
failure also leaves the new shallow file. `FetchFinishError` reports the failed phase, completed
installation and shallow effects, and the underlying transaction's per-ref/log outcomes. It does not
claim a globally atomic or power-loss-durable change. Callers must inspect the repository and start
a fresh request before retrying an interrupted publication. They must exclude concurrent depth
writers, checkout/HEAD/worktree registration changes and GC through publication. Ordinary reference
writers are protected by exact expectations.

## Local Validation and Remaining Boundaries

On macOS 26.6.2 arm64 with Rust 1.98.1 and Git 2.55.0, `just check` passed 1,848 unit tests, 1,470
integration tests and 24 doctests, nightly rustfmt, rumdl, warning-denying all-target Clippy and
docs.rs. `cargo check --no-default-features`, the disposable `fetch_remote` example, and
warning-denying private all-feature Rustdoc also passed. No dependency or format changes were
needed. Existing R27 transfer measurements remain the relevant full/known transfer baseline; this
change does not alter negotiation or pack encoding.

The full [platform validation](https://github.com/joshka/girt/actions/runs/36239103116),
[index validation](https://github.com/joshka/girt/actions/runs/36239103119), and
[reference validation](https://github.com/joshka/girt/actions/runs/36239103136) target the exact
implementation revision and all pass. The platform run passes Windows 2022, macOS 14, Ubuntu 22.04
and Ubuntu 24.04. Windows runs the portable fetch and HTTP selections; Unix runs the all-feature
fetch, HTTP and SSH suites. The earlier superseded `efc9fe83de61`
[platform](https://github.com/joshka/girt/actions/runs/36238113876) and
[index](https://github.com/joshka/girt/actions/runs/36238113902) runs failed the existing
[B04](../jj-roadmap.md#b04--intermittent-tracing-and-split-index-assertions) tracing and Windows
split-index assertions respectively; that failure history remains distinct from the successful
exact-revision results. Protocol v2 fetch and filters remain outside this workflow; R35 must assess
required v2-only endpoints. [B07](../jj-roadmap.md#b07--additional-fetch-negotiation-rounds) retains
additional have rounds. R29/R30 own push rather than fetch publication.

R28 is scoped accepted for caller-selected full-name refspec mapping, optional scoped pruning and
conditional object, shallow and reference publication on supported v0/v1, HTTP, Unix SSH and native
local paths. The four-host platform, index and reference runs above pass at the exact implementation
revision. Acceptance preserves the explicit missing-exact-ref caller policy, partial-effect recovery
contract and the listed v2, filter, B07, native-local depth and Windows SSH limits. R35 must assess
their impact on required jj integration; this status does not establish those capabilities.
