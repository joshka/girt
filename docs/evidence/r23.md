# R23 Configured Smart HTTP Evidence

R23 connects an R21 resolved HTTP destination to the existing smart HTTP fetch/push adapter.
`HttpSettings::resolve` reads a supplied configuration snapshot and explicit application
environment. `HttpRemote::configured` applies trust and proxy settings; `with_credentials` binds an
R22 session to the exact endpoint. The older explicit `HttpRemote::new` path keeps its existing
redirect-free and proxy-free behavior.

## Acceptance Boundary

- Global and URL-scoped `http.sslVerify`, `http.sslCAInfo`, `http.proxy`, and `http.followRedirects`
  are selected by scheme, host, effective port and component-bounded path. The longest path wins;
  later occurrences break ties. Explicit application environment wins over configuration for CA
  bytes, verification and proxy selection.
- Platform TLS roots and supplied PEM roots are accepted. A configured CA path requires the
  application to supply its bytes. Disabled certificate and hostname verification requires explicit
  application approval in addition to the effective setting. Proxy URLs with userinfo are refused;
  approved Basic proxy credentials are supplied separately.
- Configured connections follow one same-origin initial discovery redirect and use the resulting
  repository base for the RPC. Cross-origin redirects, redirects with origin credentials, further
  redirects and `followRedirects=true` are refused. No credential is sent to a redirected origin.
- A filled credential session is checked against scheme, host, port and repository path before a
  request. A 401 discovery response advertising Basic can retry its GET once. Other schemes do not
  receive the credential. An authenticated 200 approves helpers once per connection; 401 rejects
  them. Push POSTs are never automatically retried. A POST failure remains uncertain under the
  existing push contract, even when its HTTP status suggests rejection. The application must inspect
  remote state before a new push attempt.
- Helper lookup and prompting remain application-controlled. Notifications run synchronously in the
  async operation and retain R22's callback/process-start limits. Callers should place configured
  operations on a worker when executor responsiveness matters. URLs, header values, credentials,
  proxy settings and response bodies stay out of Debug, errors and tracing fields.

## Local Evidence

Original synthetic Python loopback fixtures in `tests/fixtures/http/server.py` serve disposable Git
repositories. `tests/fixtures/http/credential.py` records helper actions without logging secrets.
`tests/http_portable.rs` covers challenged Basic discovery and real Git upload-pack, helper
`get`/`store`/`erase` tied to HTTP outcomes, unsupported challenge refusal, same-origin redirect
through the RPC, approved Basic proxy authentication, and refusal of insecure TLS without
application approval. Transport unit tests cover URL-scoped precedence, environment override,
credential-scope refusal and Debug redaction. The pre-existing HTTP suites cover interoperability,
TLS certificate and hostname failure, cancellation, bounds, statuses, malformed framing, and
uncertain push effects. All secrets in the new tests are synthetic.

The final implementation is revision `98508e39`; the scoped published head including the separate
task-communication guidance is `0c6a58fa`. Local validation on macOS arm64 with Git 2.55.0:
`just check` passed all-feature tests, formatting, Clippy and docs.rs before the final
helper-outcome tests and bounds were added. After the last code edits,
`cargo test --all-features --test http --test http_portable` passed 48 and 18 tests;
`cargo test --all-features --lib transport::http::tests` passed 16 tests. `just clippy`,
`just docs-rs`, `cargo check --no-default-features` and `just fmt-check` passed.

## Remaining Limits and Restart Criteria

Only Basic origin and proxy authentication are implemented. Reopen other challenge schemes when an
observed required endpoint or jj consumer needs them. Cross-origin and credential-bearing redirects
need an application-approved destination policy before support; refusal is retained meanwhile to
avoid credential forwarding. Git's `followRedirects=true` multi-request behavior, `sslCAPath`,
backend-specific TLS settings, proxy authentication negotiation, and broader URL subsection matching
remain unsupported. Reopen them on a concrete endpoint/consumer failure, recording the configuration
and server behavior with synthetic secrets. Native configured-path runs remain an acceptance gate;
earlier R22 native jobs prove the helper lifecycle only.
