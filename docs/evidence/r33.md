# R33 Destructive Maintenance Safety Audit

## Initial Audit

Before implementation, R33 had no destructive API. This audit inspected the R31 scanner and R32
additive writer at executable `3eb9b07ec19dffeedf4f78f8dd9b8b30e5d50df2`. The scanner's complete
outcome establishes graph closure for a live observation, not a transaction or deletion permission.
The writer publishes a pack/index pair and retains all old storage. Its file synchronization does
not synchronize the containing directory. Removing an old copy on the strength of that publication
could lose a required object after a power failure. No existing library lock excludes an arbitrary
Git process, and the API has no inventory of readers holding an old pack generation. These are
blocking safety conditions under [A17](../jj-acceptance.md#a17--gc-repack-and-expiry).

## Required Deletion Argument

An executor must establish a caller-owned exclusion boundary before the first scan and retain it
through the final deletion and directory synchronization. That boundary must cover every producer of
roots and objects: references, reflogs, indexes, worktree and pseudoref state, loose-object writes,
pack publication and alternate-store configuration. A library lock alone is insufficient: external
Git does not acquire it. The caller must supply an isolation boundary that excludes Git processes
outside girt, with an explicit API obligation to hold it; without one, deletion must refuse. Girt
cannot verify an arbitrary external process merely from a library lock. Merely documenting an
assumed quiescent repository in a default operation would leave callers able to delete data during
an external Git write.

Within that boundary, the executor must freshly discover all roots, including caller heads, reflogs
independent of live refs, linked worktrees, recent loose objects and relevant configuration. It must
finish all bounded reads without cancellation, verify each retained object and its graph closure,
then compare the relevant source generations against their observations. A stale complete
`RetentionPlan` cannot be promoted to deletion authorization. The scan must treat changes to root
sources, loose fanout, pack/index pairs, protection markers, alternates and shallow state as a
restart or refusal. An alternate is a read source only: it is never owned for deletion, and a
required object must exist in durable owned storage before any owned copy is removed. `.keep` packs
and recent packs must remain protected.

If reflog expiry is composed with pruning, the executor must prepare the exact retained records and
resulting roots before mutation. Files and reftable stacks need separate conditional publication
rules. A changed log must refuse, and failure after one log publication needs a structured
partial-effects report. The executor must rescan after expiry before deciding which objects are now
unreachable. Expiry cannot be inferred from a plan made before its own mutations.

The replacement pack and index must be complete and independently readable before deletion. Their
files and directory entries must be made durable in the required publication order, including
parent-directory synchronization where supported. A platform where that durability cannot be
established must refuse old-copy deletion. Windows can deny unlinking an open pack; this must be
reported as a partial outcome without removing another required copy. Readers pinned to old packs
must be closed, explicitly retired or guaranteed a still-present old generation. A new reader's
successful refresh is not proof that every old reader has retired.

The deletion phase needs a journal or equivalent recoverable sequence and a structured result
listing every reflog, loose object and pack artifact actually changed. Cancellation before mutation
must leave storage unchanged. Cancellation after the first mutation, permission errors, disk-full,
process interruption and publication or unlink failures must never be reported as a clean atomic
failure. A retry must discover current state afresh and preserve all copies needed for recovery.
Object and generation checks immediately before each destructive step remain necessary even after
the initial scan; they do not replace the writer exclusion boundary.

## Evidence Needed to Resume

- Add an explicit caller isolation contract with a lifecycle covering the whole mutation window and
  a refusal path when external writers or old readers cannot be excluded.
- Make replacement publication crash durable on supported filesystems, or limit deletion to an
  independently durable owned copy. Test interruption at pack and index publication, directory
  synchronization and every old-copy deletion boundary.
- Add bounded generation snapshots and compare roots, recent objects, pack/index/protection state,
  alternates and shallow state before mutation. Test deterministic ref, reflog, loose-object and
  pack races, including a writer that appears after the first scan.
- Implement conditional files and reftable reflog expiry with retained-record validation and
  structured partial outcomes; rescan roots after expiry.
- Compare retained object IDs and `git cat-file` usability with independent Git observations in
  SHA-1 and SHA-256 repositories. Cover protected packs, alternates and pinned readers on native
  Linux, macOS and Windows. Measure temporary disk, memory, descriptors and a representative
  Criterion maintenance workload.

## Bounded Loose Pruning Slice

`Repository::prune_unreachable_loose` accepts a caller implementation of `MaintenanceIsolation`, a
retention policy and a cancellation flag. The isolation guard must exclude all girt and external Git
writers, old dependent readers and repositories using this store as an alternate for the entire scan
and deletion window. If that boundary cannot be held, acquisition must refuse. This is an explicit
caller obligation; girt cannot infer it from a lock file.

The operation makes two complete retention scans and two bounded loose-object inventories under the
guard. It checks matching roots, reachable sets, protected packs, alternate stores and candidate
metadata before mutation, then checks each candidate's metadata immediately before unlink. It
deletes only primary loose objects older than the cutoff and outside the closure of **all** observed
roots. Reflog expiry cutoffs are deliberately ignored for this slice, so every imported record
continues to retain its old and new IDs. Packs, reflogs and alternate stores are untouched. The
operation does not depend on R32's published pair or its durability. A deleted object was not needed
by any observed root, so crash recovery cannot require its replacement pack. This scope is safe only
when the caller's external isolation obligations are actually true.

`PruneFailure` distinguishes isolation refusal, incomplete scans, changed observations, cancellation
and I/O. It returns known successful deletions and identifies an uncertain target if unlink reports
an error. A retry must rescan. Cancellation after one unlink reports that completed prefix. The
candidate inventory and report are bounded by `RetentionPolicy::max_entries`; there is no pack-sized
temporary artifact. Unlink may fail on Windows when a file is open; the result names the candidate
and keeps subsequent files. Directory entries are not synchronized: after process interruption a
deletion prefix may have happened; after power loss, an unreachable object may reappear. This cannot
make a required object disappear because the slice never deletes one under its stated isolation
boundary.

Both-format integration cases use original Git-created objects, refs and reflogs; `git cat-file`
continues to read the live tip and deleted-name reflog history after pruning an unrelated loose
blob. A refusal case shows the orphan survives when isolation acquisition fails. Focused units
inject a new Git root between the two scans, cancellation after one unlink and a permission fault at
the second unlink. The first refuses without deletion; the latter two return a known prefix and the
fault names its uncertain target. A stale-handle test changes shallow state after opening and
verifies that the sweep retains the newly required parent. These cases do not establish isolation
from an arbitrary external Git process; that is the caller's repository ownership contract.

On macOS arm64 with Rust 1.98.1 and Git 2.55.0, `just check` passed 1,864 unit tests, all
integration suites including 30 retention cases, 25 doctests, all-feature/all-target Clippy and
docs.rs with warnings denied. The focused prune unit cases, both-format integration cases, nightly
formatting and Markdown formatting passed. The Criterion `prune/idempotent-packed-linear-256`
workload measured a warm sweep of a 256-commit packed history with no deletion: 20-sample estimate
24.554 ms (24.400–24.712 ms). A second run estimated 25.098 ms (24.804–25.403 ms). The latter
process had 20,119,552 bytes maximum resident set size under `time -l`, including Git fixture setup,
Criterion and the process runtime. This is a steady-state scan cost, not deletion throughput or peak
memory at the configured entry limit. The candidate list and result grow at most with the entry
budget; there is no pack-sized temporary output in this operation.

The focused [native validation run](https://github.com/joshka/girt/actions/runs/36262503439) passed
at executable revision `63c6e445f763dbeee56c5104b3e57f87d59e01bf` on Ubuntu 22.04, Ubuntu 24.04,
macOS 14 and Windows 2022. Each host ran the no-default-feature retention integration suite, the
deterministic prune fault/race units and warning-denying library/test/benchmark Clippy. The run used
Rust 1.98.1; Windows used Git 2.55.0.windows.5. The validation bookmark
`joshka/r33-loose-validation` was pushed for evidence, not merged or released. This follow-up
documentation change does not alter the tested executable.

Reftable expiry, pack retirement and full maintenance composition remain open. Native Windows and
Linux execution of the loose-pruning slice passes; disk-full behavior for any future publication,
old-pack reader retirement and deletion-throughput measurement remain unverified. R32's four-host
focused run establishes additive publication only.

## Reflog Source Identity Prerequisite

The R31 planner previously keyed expiry positions only by `RefName`. Two worktrees can each own a
private `HEAD` history at the same name, while every worktree's scan also rediscovers shared logs.
Those positions cannot authorize mutation of either stored log. The planner now keys candidates by
`ReflogSource`, combining the owning common or private Git directory with the byte-preserving name,
and visits each stored history once. Both-format Git worktree fixtures verify separate private
`HEAD` positions and one shared deleted-name history. This change only corrects the advisory plan;
it does not expire records or grant deletion authority. The focused
[native validation run](https://github.com/joshka/girt/actions/runs/36263075526) passed the
retention suite and warning-denying Clippy on Ubuntu 22.04/24.04, macOS 14 and Windows 2022 at
`2b5f7e6d0501aa6bda90eab7985258e78c9e1c84`. The validation bookmark
`joshka/r33-expiry-source-validation` was pushed for evidence, not merged or released.

## Isolated Files Reflog Expiry Slice

`Repository::expire_reflogs` uses the same caller-owned `MaintenanceIsolation` guard. It refuses
reftable before mutation and refuses files expiry on platforms without a verified directory sync. On
Unix it performs a fresh complete retention scan, prepares the exact bytes retained by the policy's
live and unreachable cutoffs, repeats the scan and checks the source bytes before replacing any log.
Each rewrite synchronizes a temporary file, atomically replaces the log and synchronizes the
containing directory before reporting success. This relies on a local filesystem honoring those sync
calls. Original retained record bytes and order are preserved; an empty result stays as an empty log
file. The operation never prunes objects. A fresh rescan remains necessary before later object
pruning.

The result identifies logs whose replacement reported success. Cancellation after a replacement and
I/O during a later replacement return the known prefix; a failed replacement names its uncertain
log. If directory synchronization fails after replacement, that log is uncertain. A process
interruption can leave a durable prefix of expired histories. Object storage is untouched, and the
caller's isolation guard must exclude external Git writers and old readers for the whole operation.

Original Git-created SHA-1 and SHA-256 repositories verify that eligible deleted-name records are
removed while live Git objects remain readable. Focused units inject a log append after preparation,
cancellation after the first replacement, a permission error at the second and a directory-sync
failure after publication. The append refuses before publication; the other faults report a partial
prefix and an uncertain target where appropriate. Isolation, reftable and unsupported-durability
refusals leave storage unchanged. Native validation of this slice remains pending.

On macOS arm64 with Rust 1.98.1 and Git 2.55.0, `just check` passed 1,867 unit tests, all
integration suites including 36 retention cases, 25 doctests, all-feature/all-target Clippy and
docs.rs with warnings denied before the directory-sync correction. After that correction, 10 focused
no-default-feature maintenance units, 36 retention integration cases, all-feature/all-target Clippy
and docs.rs passed. The Criterion `reflog-expire/noop-packed-linear-256` workload measured a warm
scan of a 256-commit packed history with no eligible log: 20-sample estimate 27.099 ms
(26.714–27.622 ms). A second run estimated 27.289 ms (26.902–27.956 ms) and measured 20,217,856
bytes maximum process resident set size under `time -l`, including Git setup and Criterion. This
does not measure rewrite throughput or peak memory at the configured log limits.
