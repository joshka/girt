# R37 Reftable Acceptance Plan

R37 is in progress. The staged implementation has local evidence; native acceptance remains pending.
R16 coordinator acceptance is the separate parent change `5ef523dc96468e0deaf35c34ae6152dd8885d2bc`.
The executable specification input is the published
[reftable format](https://git-scm.com/docs/reftable); compatibility fixtures must be generated
independently with Git commands and original byte encoders. Upstream implementation and test sources
are excluded.

## Atomic Stages and Acceptance

1. **Record codec:** Read and write SHA-1 version 1 and SHA-256 version 2 headers, reference
   records, peeled values, symbolic values, deletion records and compressed reflog blocks. Validate
   footer CRC, block framing, restart offsets, key order, update indexes, truncation, integer
   overflow and bounded decompression. Exercise aligned and unaligned tables, indexes, log-only
   tables and empty tables from independently generated Git repositories.
1. **Stack reads:** Parse bounded `tables.list` entries without path traversal, merge references and
   reflogs by stack precedence, apply tombstones, preserve record ordering, and read coherent pinned
   generations during publication and compaction. Specify cancellation, byte, record, table and
   handle budgets; test missing/replaced tables without hidden unbounded retries.
1. **Publication and compaction:** Hold Git-compatible stack locks while checking expected values,
   publish immutable tables before replacing the list, and retain explicit outcomes at every failure
   boundary. Cover contention with Git, conditional stale writers, interrupted table/list
   publication, cleanup and compaction preserving references and retained reflogs. Compaction must
   coordinate with writers and readers without discarding concurrent updates.
1. **Reference API integration:** Select the backend from repository configuration and retain the
   existing reference-domain entry points. Cover stored and resolved edits, all expected-value
   predicates, symbolic HEAD logging, no-log updates, ref/log deletion and namespace conflicts.
   Characterize linked-worktree common/private stacks and mixed-stack transactions before deciding
   their publication contract. Unsupported required behavior needs a named queued owner.
1. **Completion evidence:** Demonstrate Git-to-girt and girt-to-Git committed-tip, reference and
   reflog observations in both formats, including a nonempty repository. Add deterministic fault and
   race cases, representative Criterion stack/read/write/compaction measurements and separate
   resource observations. Run affected native suites on Ubuntu 22.04/24.04, macOS and Windows;
   retain exact executable revisions, run URLs, artifact fingerprints and failed attempts.

Each implementation stage remains separate until its relevant checks pass. Opening a repository
alone does not establish correct import: R14's unchanged jj baseline omitted the committed reftable
tip. Final consumer integration remains R35. C02 retains existing tracing, malformed-alternate and
platform owners. R40 retains imported files-reflog interpretation; R37 must state any distinct
binary-record representation limit explicitly. Pack performance work is outside R37.

## Integration Inventory

The current `References` API routes reads, enumeration, reflogs, conditional writes and prepared
transactions directly to the files backend. Repository opening rejects reftable. Integration must
include prepared transactions used by colocation, not only `References::transaction`, and must
preserve explicit partial effects when one operation spans different storage publication units.

## Codec Observations

The initial codec corpus uses Git 2.55.0 on macOS arm64. Git-generated SHA-1 and SHA-256
repositories establish committed-tip, symbolic HEAD, reflog and multi-block compacted-table reads.
Git `show-ref --head`, `reflog show` and `refs verify` accept independently re-encoded tables with
matching observations. Original binary fixtures cover tombstones, peeled values, empty/log-only
tables, full unsigned timestamps, raw identity/message bytes, truncation and resource refusals.

A Git-generated reflog deletion exposed two distinctions from a literal reading of the published
format: a log-only table can locate its first block at offset zero with header-inclusive inflated
length/restart offsets, and a new transaction table can rewrite older reflog keys below its minimum
update index. The decoder accepts these observed forms. Initial failing tests remain development
history, not native acceptance evidence. Stack, transaction and native acceptance remain pending.

## Implementation and Public API

The `refs::reftable` module owns original bounded table codecs, binary record types, merged stack
snapshots and explicit compaction. `RecordName` preserves uppercase pseudorefs discovered in
Git-created linked-worktree tables; ordinary reference edits retain `RefName`'s existing scope. No
dependency is added. `refs::Backend`, `Repository::reference_backend` and
`Repository::init_with_backend` expose backend selection. Existing read/list/resolve/no-log writes,
reflogs, conditional transactions and colocation use the selected backend.

`Repository::open_with_config_and_reference_limits` bounds real-HEAD configuration bootstrap;
`References::with_reftable_limits` bounds later operations. `transaction_controlled` adds
cooperative cancellation with structured partial effects. `Snapshot::read`, `Table::decode`,
`Table::encode` and `compact` provide standalone binary storage operations. The
[transaction contract](../reference-transactions.md#reftable-backend) records consistency,
resources, publication, cleanup and durability limits.

Local deterministic cases cover a Git writer excluded by held stack locks, stale expected values
after Git publication, cancellation before writing and between common/private publications, and
injected failure after immutable table creation but before list replacement. The last failure
preserves old visible records and leaves an ignored unlisted table. Native evidence remains pending.

Git-created linked-worktree tables contain `ORIG_HEAD`; compaction retains this binary record even
though ordinary reference operations do not expose it. Git also expects a terminal newline in a
binary reflog message. Backend append adds that delimiter; interpreted reads remove one delimiter;
the raw codec remains byte-preserving. The initial failing interoperability assertions identified
these boundaries before acceptance. No upstream implementation or test source was read.

## Remaining Owners

R40 must characterize consumer interpretation of binary reflog timestamps above `i64::MAX`,
alongside its imported files-reflog work. R37 preserves the complete unsigned field and compacts it
losslessly; `References::reflog` reports an explicit interpretation limit. R19/R20 retain
operation-specific pseudoref mutation policy; R37's codec and compaction preserve uppercase records
without extending ordinary edit names. These boundaries must remain visible at R34/R35 rather than
being treated as Git-invalid data. R38, R40, then R17 remain the next serial sequence; this task
dispatches none.

The implementation deliberately uses bounded whole-table decoding and full-stack compaction. Point
lookup decodes a stack; no near-constant lookup performance claim is made. Compaction holds writer
locks throughout its bounded work. Automatic compaction, orphan collection and log expiry are not
added; callers explicitly compact before configured stack budgets are exhausted. R31/R32 retain
maintenance planning and publication policy. No pack optimization is included.
