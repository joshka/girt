# R31 Retention Planning Evidence

## Capability and Boundary

`Repository::plan_retention` takes `RetentionPolicy` with caller-retained heads, a recent-object
cutoff, reflog expiry cutoffs and scan budgets. It returns a read-only `RetentionPlan` with root
candidates, the complete candidate closure, the closure required after planned reflog expiry,
per-log record positions eligible for expiry, protected pack paths and discovered alternate stores.
`References::list_controlled` bounds files reference bytes and directory entries, while
`References::imported_reflog_names` inventories files and reftable histories independently of live
reference names. `Objects::store_directories` exposes the reader's canonical primary/alternate
search order. No repository files change. The API supports SHA-1 and SHA-256.

The planner reads shared references and every registered worktree's private refs, HEAD, index and
logs. It includes caller heads, known object-bearing pseudorefs, recent loose objects, and both
old/new IDs from each imported reflog record. It follows commit/tree/tag edges and stops commit
ancestry at declared shallow boundaries. Gitlinks remain external. A record is considered live when
either endpoint is reachable from non-reflog roots; the caller's live or unreachable cutoff then
determines whether it is an expiry candidate. Even eligible records stay in the candidate closure,
so inspection can see what would be lost. `required` retains the closure of all strong roots plus
unexpired records.

`RetentionOutcome::Incomplete` preserves recovered candidates and refuses to present a complete set
after a missing object, invalid graph edge, corrupt log, changed/deleted discovered log, resource
limit, cancellation or failed I/O. Precious-object repositories, partial clones and
`gc.recentObjectsHook` refuse complete planning. Caller cutoffs replace Git's prune and reflog
expiry config; the defaults retain every existing loose object and imported history. Other GC
packing choices do not affect this read-only inventory. Pack content is not a deletion candidate;
`.keep` and recent pack paths are reported for R32. Alternate stores supply reads but are never
owned for pruning.

A complete plan is a live observation. Reference, reflog, index, worktree and loose-object reads do
not form an atomic snapshot, even though pack readers pin an immutable pack generation. R32/R33 must
exclude cooperating writers, rediscover roots and recent objects, verify the pack generation and
perform publication/pruning within that execution boundary. This report does not authorize pruning
after writers resume. Uncoordinated path replacement and network filesystems remain outside the
existing storage contract. R32 owns atomic pack/index publication and fault probes; R33 owns
destructive pruning, reflog mutation, and end-to-end maintenance composition. A17's interrupted
writes, repack races, disk-full, permissions and post-publication cancellation remain open for those
execution tasks.

## Independent Git Observations

`tests/retention.rs` creates isolated repositories with Git 2.55.0 operations. It uses
`git init --bare`, `mktree`, `commit-tree`, `update-ref`, `worktree add --detach`, `hash-object -w`,
`update-index` and `cat-file`, then compares the planner's observed closure with
`git rev-list --objects` and `git rev-list --objects --all --reflog` for SHA-1 and SHA-256. The
deleted files reflog is an original record written to an independently generated Git repository. A
reftable fixture uses Git to create a reflog and girt's explicit no-reflog deletion to retain
history after the live ref disappears. The tests check a detached linked HEAD, an unavailable
checkout with private HEAD, and a private index, expiry classification, pseudoref roots, corrupt
history, missing objects, resource limits, cancellation, kept packs, alternate ownership and the
recent-objects hook gate. The Git closure comparison covers the selected roots; it does not
establish parity for every Git GC configuration or expiry heuristic. With reflog expiry set to
`never`, `git gc --prune=now` on disposable repositories retains exactly the planner's `required`
set in both formats according to `git cat-file --batch-all-objects`; `git cat-file -t` still reads
both commits. Girt performs no mutation in these tests.

## Validation and Remaining Evidence

Local validation used macOS Darwin, Rust 1.98.1 and Git 2.55.0. The retention integration suite
passes nineteen cases. `just check` passes whole-crate tests, all-target/all-feature Clippy, nightly
formatting, rumdl, doctests and docs.rs. Focused all-feature and core-only retention runs each pass
19 cases. `actionlint` passes the platform workflow. `benches/retention.rs` measures the full
read-only plan over an original 256-commit linear Git history in a pack, with fixture construction
outside the timed operation and warm filesystem cache. Its 20-sample estimate was 15.671 ms with a
15.587–15.762 ms interval. This is a planning baseline; it does not measure R32/R33 disk use or
maintenance throughput. Allocation is bounded by caller limits on root/record counts, aggregate
retained reflog bytes, files reference bytes and entries, graph objects/edges/decoded bytes, and the
existing per-index, per-log, reftable, pack and alternate budgets; allocator overhead and filesystem
metadata are additional. The
[first native run](https://github.com/joshka/girt/actions/runs/36257445674) passed the focused
matrix on Ubuntu 22.04/24.04, macOS 14 and Windows 2022 at the initial executable revision. A
revised run is pending for bounded reference inventory. The platform workflow includes
`tests/retention.rs` in Unix core-only and Windows portable selections; Unix all-features already
runs the complete suite.
