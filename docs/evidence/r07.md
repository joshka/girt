# R07 — Imported Objects and Tag Peeling

R07 implements tolerant object reading under
[A01](../jj-acceptance.md#a01--commit-identities-timestamps-and-signature-payloads) and
[A04](../jj-acceptance.md#a04--object-representations-and-git-interpretation). Its parent is the
unchanged R06 evidence change `9a38f9c36220690e32976990e1925fe52124bd34`, above native-tested
`f79b50843a47aeed7b468acb7b4a133f35e98a10`. No jj source, adapter, publication or merge is included.

## Public Calls and Representation

`Tree::parse` interprets octal mode type and owner-execute bits, including historical permissions,
leading zeros and large numeric spellings. Only the relevant low bits affect interpretation; other
numeric types follow Git's gitlink interpretation. Non-octal text still fails. Original mode bytes,
names, order and IDs remain intact through encoding, hashing and loose reads/writes. `Tree::new`
still emits canonical modes and sorts validated names; `Tree::validate` checks names/order without
requiring canonical mode spelling. Hashing now reads the retained payload without re-encoding it.

`Commit::parse` decodes a leading tree and contiguous parent records in the selected format. Those
records require exact-width IDs and LF terminators. Later tree/parent records do not add or replace
graph edges. A short trailing parent-like fragment is metadata rather than an edge. A payload ending
immediately after complete graph records fails, matching the exercised Git reader. Missing people,
reordered/repeated person headers, physical continuations, malformed dates, opaque lines, absent
separators and unterminated metadata remain readable. `tree`, `parents` and `message` expose usable
graph/message values. The last physical `author` or `committer` wins; continuations do not extend
identities. The original payload remains the source of object identity.

`IdentityRef::parse` borrows raw name, email and date bytes. The first opening and following closing
bracket select the email; trailing ASCII delimiter whitespace is removed from the name. Commit
`author`/`committer` and tag `tagger` return `Result<Option<IdentityRef>, ...>`: absence and
malformed identity framing remain distinct. `IdentityRef::date` returns `IdentityDate` with signed
`i64` seconds and `i16` offset minutes. Short/padded zones, optional whitespace, numeric zone
prefixes and noncanonical HHMM fields have explicit arithmetic interpretation. Missing, malformed
and overflowing numbers return `InvalidDate`; no epoch fallback is invented. Raw identities remain
accessible after date failure. `Signature::parse` composes these operations. Reflog parsing retains
its previous stricter date-framing checks at that boundary.

`Tag::parse` requires ordered, LF-terminated `object`, `type` and `tag` records. Later duplicate
known keys and opaque/folded/truncated extra records remain inspectable without overriding the
target. `target`, `target_kind`, `name` and `message` expose those values; the first physical tagger
wins, including when an unknown line precedes it. Invalid tagger dates do not block target decoding.

The old borrowed `fields` accessors are replaced by fallible, owned `Commit::to_fields` and
`Tag::to_fields`. These explicitly request editable construction fields and can fail on metadata
that graph readers do not need. Commit conversion also rejects opaque lines lacking a value
separator because `CommitHeader` cannot represent them. `new` and `validate` retain construction
policy; reconstruction can change lexical spelling, duplicate-header representation and identity.
All in-repository callers use the appropriate graph accessor or explicit conversion.

`CommitPayload::parse` retains its strict framing contract. `CommitPayload::from_bytes` additionally
indexes legacy physical records without requiring a separator or final LF. Both use exact spans for
`without_headers`, including continuation spaces, empty lines and truncated final records. The new
`CommitHeaderRef::has_value_separator` distinguishes bare legacy records from framed headers;
signature recognition must require that flag and the exact header name. Selecting spans remains
caller policy, independent of object format or cryptographic verification.

## Bounded Peeling and Consumers

`Objects::peel(id, PeelLimits, &AtomicBool)` returns `PeeledObject` with the original tip, ordered
tag identities, terminal target and verified kind. `PeelLimits` bounds tag edges, cumulative payload
bytes and each storage read's object/delta work. The remaining byte budget also caps the next read;
exhaustion during allocation can therefore surface as a structured storage limit. Memory includes
the visited IDs and one object plus its decoded view; limits are not a process-heap or time promise.

`PeelError` retains the original tip, failing ID, referring tag, depth and boxed `PeelFailure`.
Failure classes distinguish missing objects, storage corruption/I/O/read limits, malformed tags or
terminal commits, declared/actual kind disagreement, depth/byte limits, cycles and cancellation.
Terminal commits require readable graph records. Terminal trees remain uninterpreted, matching Git's
peeling operation; callers needing tree records must separately decode them. Cancellation is checked
before and after each synchronous read, with no promise to interrupt that read. All paths are
read-only and return no partial successful result.

History uses decoded commit graph access even when identities/dates cannot become construction
fields. Transfer edge discovery follows readable trees in stored order without imposing canonical
name/order validation. Tree comparison, status and checkout retain their own path-sensitive
validation. Fetch update classification uses the shared peeling operation, preserving its
no-reference-publication guarantee on failure. SHA-256 transport negotiation is still explicitly
unsupported under R26/R29; dual-format decoding does not remove that boundary.

The optional `objects.peel` span owns its read children, records categorical completion, and never
records IDs, names, content or identity bytes. Subscriber/runtime policy remains with the caller.
There is no async handoff or new tracing context ownership in this synchronous operation.

## Independent Git Observations

The original [probe](../../tests/fixtures/decoding/observe.py) runs Git executables in disposable
repositories, removing inherited Git overrides and disabling global/system config and templates.
Every fsck observation uses a fresh repository containing only the fixture and its ordinary empty
tree/blob dependencies. No upstream implementation or test source was consulted. Reproduce with:

```sh
python3 tests/fixtures/decoding/observe.py > /tmp/r07-git-observations.json
```

The [retained JSON](r07-git-observations.json) records exact payloads, IDs, exit codes,
stdout/stderr, Git version and platform for SHA-1 and SHA-256. `hash-object --literally`/`cat-file`
establish raw storage only. `show`, `rev-list`, `ls-tree`, tag peeling and tagger formatting
independently establish interpreted behavior; ordinary `hash-object` and isolated `fsck --strict`
establish different construction/validation outcomes.

- Git reads historical/padded/large octal modes and preserves record order. Canonical writing/fsck
  reject the exercised noncanonical modes and unsorted trees. Girt preserves imported bytes while
  exposing interpreted entry kinds.
- Missing/reordered people, duplicate known headers, continuations and opaque legacy lines can be
  traversed despite writer/fsck failures. A late parent does not become a graph edge. The leading
  tree remains authoritative; author/committer display uses the last physical occurrence.
- Negative dates are preserved numerically by girt while Git display emits empty date fields.
  Malformed/missing dates retain usable identity bytes. Overflow beyond `i64` is an explicit
  interpretation error even where Git prints an unsigned value or a fallback formatted date. `+2400`
  has arithmetic meaning and is displayed by Git; `-0060` is numerically interpretable but the
  exercised Git formatted display fails. Short zones and numeric suffixes can display despite fsck
  rejection. These are distinct observations, not one undifferentiated acceptance claim.
- Tags with absent or malformed taggers still peel; mandatory target framing remains ordered and
  terminated. Later known headers do not replace those target records. A malformed terminal commit
  prevents peeling; a malformed terminal tree payload does not prevent kind/identity resolution.
- A deliberately failing verification process captures the actual payload and signature bytes
  supplied by `verify-commit`. Both hashes remove both signature-header spellings from the payload.
  SHA-1 selects/concatenates `gpgsig` occurrences; SHA-256 selects `gpgsig-sha256`. Legacy opaque
  records survive byte-identically. No test claims cryptographic validity or chooses jj policy.

## Acceptance and Remaining Owners

The public `decoding` suite and local units cover both formats, original Git differential inputs,
exact round trips, signed payload captures, raw identities, ambiguity rules, date errors, malformed
and truncated records, storage/history integration, nested tags, terminal kinds, wrong-kind/missing/
corrupt targets, exact/exhausted limits and cancellation. A private injected reader exercises cycle
and cancellation-after-read guards: constructing a content-addressed hash cycle is not a feasible
public fixture. Existing malformed storage, pack, publication/fault and transfer suites retain their
contracts. Pure decoding has no external effects; peeling corrupt storage leaves its bytes intact.
No new mutation or race protocol requires an additional publication-race harness.

R01's four R07 follow-ups are resolved by numeric interpretation with raw-byte access, decoded graph
access independent of people, characterized legacy framing, and both-format storage/signature
coverage. R04's historical modes/order and nested-peeling follow-ups are resolved here. Structural
byte retention alone is not used as decoded acceptance evidence.

R26/R29 retain SHA-256 negotiation and transfer-specific budgets; R35 retains jj's fallback dates,
placeholder identities and signature-provider selection. R34 must refresh the independent corpus and
native acceptance evidence; R36 retains the Windows integration inventory. No additional large
required capability was discovered in this slice. This finite corpus does not establish universal
Git or jj parity.
