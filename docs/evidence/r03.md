# R03 — Optional Operation Tracing

R03 implements the operation-observability increment of
[A03](../jj-acceptance.md#a03--instrumentation-errors-and-scheduling). R02 remains unchanged at
`dbd744f51844aaf7f9d8ff5db93fbdf91516abba`. No jj consumer, adapter, publication or merge is
included. The [tracing contract](../tracing.md) lists exact coverage, fields, levels, ownership and
exclusions.

## Public Behavior and Architecture

The new optional Cargo feature is `tracing`. Existing calls gain DEBUG operation/phase spans and
TRACE storage spans on the `girt` target. Covered domains are loose/packed object access, history,
fetch validation/install, local/HTTP/SSH transfers, push preparation/acknowledgements, reference
transactions, index storage, and composed fetch/clone completion. There is no public telemetry
module, new public call, subscriber installation, event framework, retry, or scheduling layer.
`src/trace.rs` privately classifies concrete errors and owns download tracing context.

Spans expose categorical outcomes, aggregate work/resource counts and partial/uncertain publication
boundaries. They never format input arguments or returned errors. Push reports distinguish transport
success from rejected references through safe acknowledgement counts. Subscriber-owned timing can
measure busy/idle lifetimes; retained download parents include queue and validation time. Errors,
reports and source chains retain their existing recovery authority.

`DownloadedFetch` retains the caller's span and dispatch when tracing is enabled. Validation and
abandonment on another worker use that dispatch and restore the worker's previous context. The value
remains `Send + Sync + 'static`, and network futures retain their conditional Send behavior. Tests
caught and fixed parent-span release under the wrong subscriber, and verify that filtered child
operations cannot overwrite caller fields. Async inner-future destruction occurs inside its
operation span; no entered guard crosses suspension.

One public error variant is added: `Error::UnknownObjectType` identifies unknown loose header kinds.
`Error::UnsupportedObjectType` continues to identify a recognized kind mismatching the typed reader.
Previously both cases used the latter variant, preventing distinct unsupported/wrong-kind
classification. Original compressed fixtures verify typed and raw reads, without changing accepted
object formats or writing policy.

## Overhead Measurements

`benches/tracing.rs` measures a cached 4-KiB loose blob read and a 128-commit loose-history walk.
Repository construction is outside timing. Each workload uses 30 samples, one second warmup and at
least two seconds collection. The interested subscriber formats TRACE-level closed spans with
busy/idle timing to an I/O sink; this includes formatting costs but excludes terminal/disk output.
Run `cargo bench --bench tracing`, then `cargo bench --features tracing --bench tracing`.

| Configuration                       | Cached blob mean (95% interval) | History mean (95% interval) |
| ----------------------------------- | ------------------------------- | --------------------------- |
| Feature disabled                    | 27.40 µs (26.59–28.75)          | 3.260 ms (3.218–3.301)      |
| Enabled, no subscriber              | 26.82 µs (26.55–27.11)          | 3.285 ms (3.235–3.330)      |
| Enabled, interested formatting sink | 28.18 µs (27.91–28.46)          | 4.119 ms (3.740–4.737)      |

The disabled/no-subscriber intervals overlap; these filesystem workloads do not resolve a small
instrumentation-check cost. TRACE formatting adds observable work across repeated history reads,
with substantial run variance. Results establish no speedup, universal overhead percentage, or
numerical gate. Preliminary runs overlapped compilation and were superseded by these sequential
final runs. [Raw Criterion samples and estimates](/Users/joshka/.codex/reports/girt-r03/criterion),
[commands and source hashes](/Users/joshka/.codex/reports/girt-r03/benchmarks.json), and the final
logs remain available. Hot pure hashing/parsing loops receive no new instrumentation.

## Dependencies and Minimums

`tracing = "0.1.40"` is optional with only `std`; no attributes or log bridge are requested. Correct
drop-time span entry for instrumented futures was introduced in 0.1.38; 0.1.38 and 0.1.39 are
yanked, making 0.1.40 the earliest selectable release with that contract. The isolated
[minimum-version probe](/Users/joshka/.codex/reports/girt-r03/minimum.log) compiles this source with
exactly 0.1.40, including tracing+SSH. It is a tracing-minimum check, not a whole-graph MSRV claim.
The lockfile keeps 0.1.44. `tracing-subscriber = "0.3"` is development-only for tests, the example
and benchmarks, with only `fmt` and `registry`. It is not a library runtime dependency.

Registry manifests declare MIT for tracing, tracing-core, tracing-subscriber and sharded-slab;
lazy_static and thread_local declare MIT OR Apache-2.0. Existing dependency requirements are
unchanged. The feature-disabled core has no normal tracing dependency; HTTP's preexisting dependency
graph may include tracing independently.

## Follow-Ups and Limits

- Each new operation extends A03 according to the
  [instrumentation guidance](../tracing.md#cost-and-future-instrumentation). Current uninstrumented
  domains are listed explicitly in the coverage contract.
- R26 must revisit structured effects for direct `ReceivedFetch::install` failures. Its existing
  `FetchError` can accompany an unindexed published pack; tracing now exposes the phase, but callers
  without a subscriber still need the documented inspection contract. A structured installation
  report belongs with that API's transfer redesign. Existing composed finish reports are preserved.
- R26/R29 retain replacement of local Git executable transfer adapters. R03 observes their complete
  process lifetime without expanding or replacing them. R35 remains the sole jj integration task.
- Native Linux/Windows runtime evidence remains pending. Cross-compilation does not prove cleanup,
  races or subscriber behavior on those platforms. R04 is next in the serial queue.
