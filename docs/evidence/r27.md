# R27 Fetch Transfer Evidence

R27 extends upload-pack transfer in both object formats. V0/v1 wire requests use advertised tip IDs,
one bounded have batch, and an optional positive depth. HTTP and Unix SSH adapters use their owned
v0 connections; native local transfer continues to read girt storage directly. The caller owns
history preparation, selection, cancellation, installation, and reference policy.

## Verified Transfer Boundaries

`KnownHistory` verifies objects reachable from explicit roots and stops parent traversal at declared
shallow commits. It sends those relevant boundaries to the peer. A depth request returns the
server's resulting shallow roots. Connectivity checks stop at those commits while still checking
their trees. A result with shallow roots refuses ordinary installation, since pack and shallow
metadata must be published together by the later installation workflow. Existing shallow
destinations also remain excluded from ordinary installation. The depth APIs therefore provide
validated transfer results and boundary data, not a complete shallow-clone workflow.

When the peer advertises `thin-pack` and verified haves are offered, the client can receive a
REF_DELTA based on a local object. It verifies the external base's identity, reconstructs the
received object, and writes a self-contained pack/index before returning success. Missing or corrupt
bases fail without an installable result. Completion is bounded by the pack byte and decode budgets;
a thin input that cannot fit its completed form fails explicitly. This may use a second pack-sized
buffer during validation.

## Git Fixtures and Validation

The Git 2.55.0 fixtures create fresh SHA-1 and SHA-256 repositories. Caller-owned v0/v1 sessions
fetch and install complete histories in both formats. Separate fixtures request depth one, verify
the boundary, and deepen verified Git-created shallow history. HTTP and Unix SSH fixtures check
SHA-256 complete transfer and depth responses. Git `pack-objects --thin --revs` produces an external
REF_DELTA in both formats; girt rejects it without the base, resolves it with the verified base, and
makes a readable complete pack. Unit cases check corrupt bases, malformed shallow responses and
resource limits. Existing transfer suites cover initial/incremental negotiation, sideband,
truncation, cancellation and installation dependency checks.

## Resource Baseline

The existing `benches/fetch.rs` local transfer workload on macOS arm64 uses Git-created 19-object
and 259-object histories. In the 19-object case, a new child commit requires a 39,662-byte full pack
or a 192-byte known-history pack. The 259-object case requires 629,089 bytes or 193 bytes,
respectively. The 10-sample Criterion run with one-second warmup and measurement reports median
transfer times of 2.765/1.427 ms for full/known at 19 objects and 35.586/14.740 ms at 259 objects.
Knowledge preparation is separate; its 259-object median is 13.412 ms. These are warm local
pack-construction measurements, not network timings. The
[Criterion log](../benchmarks/r27-transfer/criterion.txt) retains workload sizes, intervals and tool
output.

Two direct benchmark-process runs of the 259-object functions under macOS `/usr/bin/time -l` report
peak resident sets of 64,946,176 bytes for full transfer and 53,084,160 bytes for known transfer
([full](../benchmarks/r27-transfer/full-256-rss.txt),
[known](../benchmarks/r27-transfer/known-256-rss.txt)). These peaks include fixture construction,
Criterion and process overhead; they are not per-operation heap measurements. Explicit wire, pack,
decoded-object, known-history and resolution limits provide the enforced resource bounds.
Cancellation and truncation tests assert failure before an installable result is returned.

The exact tested code revision is `1de297c12faaed63d9168adb86e6740c761ab528`, published at
`joshka/r27-fetch-transfer` on top of R26 evidence revision
`1eb20cdc49da2192eaadaa68d96802813b184261`. On macOS 26.6.2 arm64 with Rust/Cargo 1.98.1 and Git
2.55.0, `just check` passes 1,846 unit tests, 1,460 integration tests, 24 doctests, nightly rustfmt,
rumdl, all-feature/all-target Clippy with warnings denied, and docs.rs with Rustdoc warnings denied.
Focused Git v0/v1, shallow, HTTP, SSH, thin-pack and SHA-256 tests also pass. The native
[platform run](https://github.com/joshka/girt/actions/runs/36236072085) uses this exact code
revision. macOS 14, Ubuntu 22.04 and Ubuntu 24.04 pass. Windows passes the discovery, shallow-layout
and SHA-256 suites and its portable HTTP runtime, but the overall job fails in the unrelated
split-index `overlapping_split_bitmaps_follow_git_deletion_order::case_2_sha256` assertion at
`tests/index.rs:872`. [B04](../jj-roadmap.md#b04--intermittent-tracing-and-split-index-assertions)
owns that native failure; the platform run is not counted as an overall pass. The concurrent
[index](https://github.com/joshka/girt/actions/runs/36236072086) and
[reference](https://github.com/joshka/girt/actions/runs/36236072089) validations pass.

Additional have rounds are tracked in
[B07](../jj-roadmap.md#b07--additional-fetch-negotiation-rounds). Protocol v2 fetch and filters
remain unsupported; R35 must check required v2-only endpoints before integration. R28 owns
coordinated shallow installation, reference mapping, pruning and conditional publication; R29/R30
own push.
