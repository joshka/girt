# R34 Unix Integration Readiness Gate

## Decision and Scope

**Go for a local-dependency integration attempt on Unix to expose actual consumer requirements;
no-go for declaring the R35 replacement complete.** R33 received separate scoped acceptance at
`812115ca0a68`. R34 reviews that executable revision and the retained R01–R41 reports; its only
source edit corrects a Rustdoc link. The integration attempt may wire and test non-destructive
operations, but must not call R33 destructive maintenance from an ordinary jj repository until the
isolation blocker below is resolved. It must not retain Git production fallbacks or claim jj
compatibility as a completed result. R35 remains the owner of the replacement and its native
consumer suites.

This is a bounded readiness review, not a new exhaustive proof of the full acceptance matrix. The
matrix combines library capability contracts with requirements that only a jj adapter can verify.
The reports linked below retain fixtures and exact tested revisions. Green reruns establish that a
suite can pass; they do not explain the original intermittent failures.

## Required Unix Maintenance Blocker

`MaintenanceIsolation::acquire` requires exclusion of every external Git and girt writer, readers
pinned to an old loose object or pack, and repositories depending on the object store as an
alternate. The guard spans scans through final deletion. R33's tests use an exclusive disposable
fixture and prove behavior **under** that premise; the library cannot verify it from a lock file.
Its second scans and generation comparisons reduce observed races but do not establish exclusion
between a final check and unlink.

In the inspected jj consumer source, `GitBackend::gc` recreates no-GC refs from the index and then
runs `git gc --prune=<cutoff>`. It explicitly relies on a recency cutoff to mitigate concurrent new
commits. The CLI `GitImportExportLock` coordinates jj import/export in colocated workspaces and is
empty outside them. Neither action prevents an arbitrary Git process from writing the colocated
store, proves old pack readers have retired, or enumerates repositories borrowing it as an
alternate. An ordinary jj command therefore cannot honestly implement the R33 guard. Replacing the
existing GC call with `run_maintenance` under that lock could delete data and is a blocker,
including on Unix. This conclusion uses the retained jj call-site inventory and the read-only
consumer snapshot at `lib/src/git_backend.rs` and `cli/src/cli_util.rs`; R35 must recheck its target
jj revision.

**B09 required follow-up:** establish a safe ordinary-jj maintenance path before replacing GC. The
shortest candidate is additive pack publication and a no-deletion maintenance mode while external
exclusion is unavailable, with bounded retained-disk growth and an explicit user-visible
deferred-reclamation result. It must preserve jj's no-GC roots and recent-object cutoff and be
tested for reopen, mixed Git writes, colocation and alternates. If GC requires actual deletion,
design and validate an enforceable isolation or another deletion proof that tolerates independent
Git writers and pinned readers. A policy that simply declares the repository quiescent is not a
resolution. R35 may test an adapter on disposable exclusive repositories, but cannot count that as
the ordinary GC integration contract.

## Transport and Observability Boundaries

R27 sends at most 32 verified haves before `done`; B07 may remain deferred if the R35 transfer
assessment finds ordinary size and latency acceptable. A required v2-only fetch endpoint is a
separate interoperability blocker because the current path explicitly refuses it. R30 returns
bounded progress after an exchange rather than live HTTP/SSH callbacks. R35 must inspect its UI and
cancellation call sites; add live delivery only if a required workflow depends on it. Native local
receive refuses hooks, proc-receive, `updateInstead`, push options, selected fsck/input-size policy
and shallow destinations. R35 must identify actual local destinations and implement any required
mode before replacement. Proc-receive has one original Git HTTP SHA-1 Unix rewrite fixture; do not
claim broader transport or SHA-256 behavior from synthetic parser cases.

B04 is not closed by passing retries. A `fetch.http` span disappeared in original macOS and Windows
runs while the HTTP operation's own result remained successful. The current code instruments the
future with an explicit span and transfers a `DownloadContext` to validation, but the failure lacks
captured dispatcher/span lifetime evidence. A fixture or subscriber problem remains possible. R35
must reproduce with complete spans and worker/dispatcher ownership and fix any demonstrated
production lifetime bug before final integration. The split-index failure occurred in its Git oracle
before girt parsed the index; C02 owns capture of the raw fixture and Git output. The final-revision
[Windows index run](https://github.com/joshka/girt/actions/runs/36295182525) reproduced that case
for SHA-256: `git ls-files --stage` was unexpectedly nonempty before girt read the index. This is
still a failing oracle observation, not evidence that girt decoded the wrong entries. Neither
failure should be reclassified as harmless merely because a subsequent run passed.

The R34 exact-tree platform run repeats B04 in two distinct cases. Ubuntu 24.04's all-feature suite
failed `interleaved_pending_futures_do_not_leak_entered_spans`: the selection closure observed
`first` instead of `fetch.http`. macOS 14's focused tracing suite failed
`abandoning_download_on_worker_closes_original_spans` with no captured `fetch.http` span. Both
operations otherwise reached the assertions; neither log establishes whether span creation,
subscriber registration or worker lifetime is at fault. Preserve these original failures for the
follow-up even if an unchanged rerun passes.

## Performance and Resource Decision

R41's matched warm buffered packed-read ratios remain 0.43–0.48x Git for ordinary SHA-1 blobs and
0.038–0.053x for selected deep deltas; its second fixture gave about 0.38–0.40x for packed blob/tree
reads across both formats. These miss A20's target and are explicit B05 exceptions, not aggregate
parity. A single macOS pass of girt-only reference/repository/tree sentinels has no matched Git
operation, and transport, writes, traversal, maintenance and complete jj workflows lack an
equivalent full corpus. More synthetic tuning before seeing jj's actual weighting would make the
gate unbounded. R35 should measure import, log, rewrite, fetch/push and GC adapter paths, then
promote a substantial ordinary regression that controls user latency. Preserve identity validation
and read limits during any optimization.

R33's original 2,050-object, 256 MiB blob-input probe observed 9.538 seconds, 275,775,488 peak
resident bytes, eight sampled open descriptors and 537,300,428 peak pack-directory bytes, about
twice the initial pack storage. Git fsck passed afterward. This is a bounded macOS observation under
exclusive-fixture isolation, not a universal limit or a jj GC performance comparison.

## Validation and Exit Criteria

The locally tested tree is `ea40964ea760a32cc9f6da91206e4b0015cca2bc`, a documentation-only child of
R33 executable review tip `812115ca0a68`. On macOS 26.6.2 arm64 with Rust/Cargo 1.98.1 and Git
2.55.0, `just check` passed nightly Rust formatting, rumdl, 1,875 library unit tests, all-feature
integration suites, 25 doctests, warning-denying all-target Clippy and docs.rs. The R34 report and
roadmap additionally pass `just fmt-md-check`. The subsequent Rustdoc link fix changes no executable
behavior and needs native revalidation.

The exact-tree native [index](https://github.com/joshka/girt/actions/runs/36294685881) and
[reference](https://github.com/joshka/girt/actions/runs/36294688727) runs passed on
`joshka/r34-native-validation`. The
[platform run](https://github.com/joshka/girt/actions/runs/36294674399) passed Ubuntu 22.04 but
failed on Ubuntu 24.04 and macOS 14 in the tracing cases above. Windows passed its portable tests
and failed warning-denied Rustdoc: `RetentionPlan` was imported only under `#[cfg(unix)]`, so an
unqualified public link in `expire_reflogs` was unresolved on Windows. R34 changes that link to
`crate::retention::RetentionPlan`. The second native Windows platform job passed warning-denied
Rustdoc at the fix revision. A local macOS-to-Windows cross-doc attempt stopped earlier while
compiling `aws-lc-sys` without Windows C headers, so it did not verify the link. The earlier R33
native matrices exercise Unix maintenance and Windows refusal, while the final review tip adds a
resource probe and documentation.

At the documentation-fix revision `2f8f27ddf859389889a07be53c902226bbe88bd0`, the
[reference matrix](https://github.com/joshka/girt/actions/runs/36295182624) passed. The
[index matrix](https://github.com/joshka/girt/actions/runs/36295182525) failed only its Windows
SHA-256 split-index Git-oracle case above. The
[platform matrix](https://github.com/joshka/girt/actions/runs/36295182482) passed Ubuntu 22.04,
Ubuntu 24.04, macOS 14 and Windows 2022, including Windows Rustdoc. This passing run does not
explain or erase the first run's two tracing failures. The exact-revision index matrix still fails
on the Windows Git-oracle fixture, so the full R34 native gate remains open. No executable logic
changed between the two native revisions.
