# R32 Additive Repack and Publication Evidence

## Delivered Boundary

`Repository::repack_retained` takes a retention policy, bounded writer options and a cancellation
flag. It runs a new complete retention scan, opens pinned source packs, reads every required object
and writes a pack v2/index v2 pair into temporary files in the primary pack directory. Both files
are synchronized before publication. The pack is published without clobbering an existing path, then
its index is published as the visibility marker. An existing checksum-named artifact is reused only
after byte comparison. SHA-1 and SHA-256 preserve object IDs. The operation never removes old packs,
loose objects, reflogs or alternate data. Protected packs remain untouched. New readers can open the
new pair; existing readers refresh explicitly.

The API performs an additive repack rather than a space-reclaiming replacement. This is the safe
publication slice while R33 owns pruning, reflog mutation and old-generation retirement. The scan is
a live observation. Callers must exclude cooperating writers for a stable maintenance view; girt has
no lock that excludes arbitrary external Git processes. Concurrent writers cannot lose objects
through this operation because it performs no deletion. If input disappears or changes, planning or
reading fails. No pack generation comparison is needed to authorize this additive publication; R33
must rescan roots and recent data, verify relevant generations, and account for pinned readers
before removing owned storage. Windows handle semantics are respected by retaining old artifacts
rather than unlinking or replacing them. External pack edits in place and unreliable network
filesystem publication remain outside the storage contract.

## Failure and Resource Contract

Cancellation, incomplete planning, missing/corrupt required objects and input limits fail before
publication. Temporary files are removed on ordinary errors. A failure after pack publication may
leave an unindexed pack that readers ignore. Cancellation after index publication returns success.
Conflicting existing artifacts are never overwritten. File content synchronization precedes each
publication, but directory entries are not synchronized, so the API does not promise power-loss
durability. A process crash can leave temporary files. No reflog expiry or destructive pruning is
performed.

Default writer bounds permit at most one million input objects, 64 MiB per payload, 512 MiB total
decoded input, 512 MiB pack output and 64 MiB index output. The implementation holds decoded
payloads in memory until writing finishes, plus the retention plan, writer metadata and one decoded
object in flight. Temporary disk use for one attempt is bounded by the pack and index limits, plus
any previously published or crash-left artifacts. These are explicit limits, not measured peak RSS
or a total process heap bound. The integration test checks reported pack/index lengths against
filesystem lengths and checks that success leaves exactly two files in the initially empty pack
directory. The Criterion workload measures an idempotent warm repack of a 256-commit packed history,
including a fresh scan, decode, compression, temporary files, sync and byte comparison with the
already published pair. It does not measure cold storage or first publication latency.

On macOS arm64, the 20-sample idempotent repack estimate was 34.234 ms (32.581–36.378 ms). A
separate `time -l` run of the benchmark process measured 20,119,552 bytes maximum resident set size;
this includes Git fixture setup, Criterion and the process runtime. Its repeated repack estimate was
34.534 ms (33.646–35.618 ms). These observations do not establish peak heap for the largest allowed
input. The size limits and controlled early-refusal cases establish the per-attempt temporary-disk
and decoded-payload bounds.

## Compatibility and Validation

`tests/retention.rs` builds both-format original repositories using Git `init`, `mktree`,
`commit-tree` and `update-ref`. After girt publishes the pair, `git verify-pack -v` validates the
index and pack, and `git cat-file -t` reads both commits. The test removes their disposable loose
copies and repeats Git reads, then reads through a refreshed pinned girt reader. An idempotent
second publication retains the checksum. Focused cases reject incomplete scans, cancellation and
writer limits before publication. Local unit tests deterministically cancel between pack and index
publication and verify the unindexed state; a conflicting existing path preserves its old bytes. The
broader R31 suite continues to exercise kept packs, alternates, reflogs and incomplete roots.

Local `cargo test --all-features` passed 1,860 unit tests, all integration suites including 24
retention cases, and 25 doctests. The later deterministic writer-race unit passed in a focused
three-case run. `cargo test --no-default-features --test retention`, all-feature/all-target Clippy
with warnings denied, nightly formatting and docs.rs with warnings denied passed. The final
artifact-size assertion passed both-format focused tests and test-target Clippy. Initial
`just check` reached Clippy after the broad tests and failed on a needless borrow in the new unit;
the fix passed focused tests and the full Clippy/docs gates. These results are macOS local evidence;
the final native [focused validation run](https://github.com/joshka/girt/actions/runs/36260625059)
passed retention integration cases and focused no-default-feature Clippy for executable revision
`3eb9b07ec19dffeedf4f78f8dd9b8b30e5d50df2` on Ubuntu 22.04, Ubuntu 24.04, macOS 14 and Windows 2022.
Each host used Rust 1.98.1 and Git 2.55.0 (2.55.0.windows.5 on Windows). Native Windows publication
and reopening passed with old pack paths retained. The validation bookmark is
`joshka/r32-native-validation`; it was pushed for evidence, not merged or released. This report's
follow-up documentation revision records that result without changing the tested executable.

The remaining R33 obligations are destructive pruning, reflog expiry, writer coordination through
the full mutation window, old-generation retirement, disk-full and permission faults during pruning,
and end-to-end maintenance composition.
