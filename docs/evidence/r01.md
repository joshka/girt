# R01: Commit Identities and Signing Bytes

R01 implements signed timestamp construction and exact header selection for signing input. It adds
structural byte access independently of decoded identity/date policy. R07 still owns broader object
decoding. SHA-256 object IDs/storage remain R02/R04/R05 work; either signature header spelling can
be inspected now.

## Public Contracts

- `Commit::new` and `Tag::new` accept the full signed `i64` seconds range through `Signature`.
  `Commit::validate` and tagger validation use the same rule. Offsets remain within ±1439 minutes.
  Empty, whitespace-padded, NUL/CR/LF-containing and angle-bracket-containing constructed identities
  remain rejected. No placeholder or collision policy is introduced.
- Public `Signature::parse(&[u8])` interprets the first `<` and following `>` as email delimiters.
  It trims ASCII whitespace immediately before `<` and skips it between `>` and seconds, preserving
  leading name bytes. Embedded brackets remain inspectable but fail construction policy. Dates still
  require signed `i64` seconds and signed four-digit `HHMM` with hours below 24 and minutes below
  60. Failed interpretation invents no fallback timestamp.
- `CommitPayload<'a>::parse`, `as_bytes`, `headers`, and `message` provide a borrowed structural
  view. Values, dates, object IDs, required-header presence/order, and duplicate required headers
  are uninterpreted. Header framing must be readable and the separator must exist. The original
  bytes stay available when `Signature::parse` or `Commit::parse` fails.
- `CommitHeaderRef<'a>` exposes borrowed `name` and folded `value`. `unfolded_value` removes one
  continuation framing space per line; it excludes the header's final LF, like `CommitHeader`.
  Providers expecting a final LF can append it explicitly; no cryptographic provider is invoked.
- `CommitPayload::without_headers(&[usize])` copies all bytes except selected complete header spans.
  Indices address all header occurrences in original order. Unsorted/duplicate selections are
  deterministic; invalid indices return `None` without modifying anything. Empty selection copies
  the payload. Other signatures, unknown headers, date spelling, IDs and message bytes remain
  unchanged. Selecting every header leaves the empty separator line.

New types are re-exported at the crate root from the private `commit::payload` module. Existing
`CommitFields`, `CommitHeader`, `Signature`, and `Commit::parse` remain available. Parsed commits
retain exact bytes; explicit reconstruction remains canonical and may change object identity. Tagger
parsing shares the identity interpretation change and signed construction rule.

## Independent Compatibility Observations

The original [probe](../../tests/fixtures/commits/observe.py) runs Git executables in disposable
repositories, with inherited Git overrides and global/system configuration disabled. Each identity
case has a fresh repository so fsck results cannot be contaminated by preceding malformed objects.
[Retained observations](r01-git-observations.json) contain exact input bytes, IDs, exit codes and
hex-encoded stdout/stderr, plus Git and platform versions. No upstream implementation or fixtures
were used. Reproduce with:

```sh
python3 tests/fixtures/commits/observe.py > /tmp/r01-git-observations.json
```

`hash-object --literally` and `cat-file commit` retain every probe. This is storage evidence, not
validation evidence. `show` decodes missing spaces before `<`, overlapping brackets, empty identity
components, raw bytes, and whitespace before seconds. Those observations establish the selected
identity delimiter rule. `fsck --strict` rejects several of those forms, while accepting empty
names/emails. Girt's construction policy remains intentionally narrower than structural access.

Negative dates survive storage but `show` emits blank date fields and strict fsck reports `badDate`.
At the positive `i64` boundary fsck succeeds while formatted display fails. Overflow, malformed
text, short timezone spelling, `+2400` and `-0060` have differing read/display/validation outcomes.
The exact distinctions are retained rather than generalized into a single claim of Git acceptance.

A temporary verification-process probe captures the actual stdin and signature file passed by
`git verify-commit`; it deliberately exits unsuccessfully and never claims signature validity. In
the exercised SHA-1 repository Git removes both signature spellings from its verification payload,
concatenates repeated `gpgsig` values, and does not invoke the provider for `gpgsig-sha256` alone.
`without_headers` makes the selection explicit: it can reproduce those captured payloads or remove
only one chosen occurrence. Tests check both policies. It does not infer which payload a given
signature originally signed. R35 must choose selection policy when integrating jj's provider.

## Acceptance Evidence

`tests/commits.rs` exercises the public API with:

- Negative author/committer seconds, both `i64` endpoints, loose writes/reads, Git IDs and
  `cat-file`.
- A caller detecting identical object IDs at epoch and decrementing committer seconds to −1 while
  leaving author seconds unchanged.
- Ordered root/single/merge/octopus parents generated independently by `git commit-tree` and
  ordinary commits accepted by strict fsck.
- Both signature names, repeated and blank/folded signature lines, selected single/set removal,
  uppercase IDs, signed/padded dates, negative zero offsets, raw identities and message bytes.
- Malformed/missing/overflow dates and unusual timezone spelling retained independently of failed
  interpretation, plus exact agreement with captured Git verification payloads.

Unit tests beside `commit` and `commit::payload` cover date boundaries, construction rules, identity
ambiguity, missing/reordered/repeated headers, orphan continuations, truncated framing, invalid
indices, removal of all headers and preservation after failed operations. Tag unit tests cover the
shared pre-epoch construction change. Existing storage fault/race/limit tests still apply; new
in-memory operations have no external mutations, cancellation, publication, or race lifecycle. They
allocate in proportion to headers, selected indices and returned bytes, without promising an
independent memory budget. Callers must bound untrusted input; truncation in a message cannot be
detected without external framing/identity.

The unchanged jj source baseline is `be5f5ebdc200593d8f1be06f11e27b485a97093d`. Its existing
`git_backend::tests::overlapping_git_commit_id` tests execute in disposable repositories for both
SHA-1 and SHA-256. They establish the consumer collision behavior without a girt adapter or edits to
jj. Placeholder identities, lossy display, default-date policy and signing providers remain jj's.

## R07 Follow-ups

**Resolved by R07:** [Retained decoding and peeling evidence](r07.md) records the public APIs,
independent observations, tested revision and remaining integration/platform owners. The following
list records the requirements assigned at this earlier completion.

These are required characterization/implementation work before R34/R35, not closed gaps:

1. Define decoded commit/tag behavior for malformed, missing, overflowing and noncanonical dates,
   including `+2400`, `-0060`, short offsets and whitespace. Preserve the distinction between
   interpreted values, Git display failure, fsck diagnostics and jj's fallback date policy.
1. Characterize decoded missing/duplicate/reordered required headers and required-header folding.
   `CommitPayload` retains structurally framed inputs, while `Commit::parse` still enforces its
   narrower required-header grammar. Structural parsing alone does not establish usability through
   `LooseObjects::read_commit`, history traversal or transfer validation.
1. Characterize headers without a framing space, orphan/tab continuations, absent separators and
   legacy truncated forms against the relevant Git operations and unchanged consumer. Extend
   decoding where required; do not treat current framing errors as a completed parity claim.
1. Extend the corpus to SHA-256 IDs/storage after R04, retaining the existing independent handling
   of both signature names. Recheck jj signature-provider selection at final integration.

R02, the format-bearing identity and hashing foundation, is the recommended next item. This finite
R01 corpus establishes the listed contracts on the exercised host, not exhaustive Git/jj parity.
