# R04 — SHA-256 Codecs and Loose Storage

R04 implements the codec, loose-storage and repository-format portions of
[A02](../jj-acceptance.md#a02--object-format-and-identity-foundations) and
[A04](../jj-acceptance.md#a04--object-representations-and-git-interpretation). It preserves R03 at
`4a9b343dafb25f84c35b4260f62ffdd0ce5af10a`. No jj consumer changes, publication or merge are
included.

## Public API and Supported Behavior

- `Tree::new(format, entries)` and `Tree::parse(format, payload)` require an explicit format,
  including for empty trees. All entries, including opaque gitlinks, must share it. Both widths
  preserve supported binary records exactly. Names/order validation remains separate from parsing.
- `Commit::parse(format, payload)` and `Tag::parse(format, payload)` check textual reference widths.
  Construction derives format from the commit tree or tag target; commit parents must match the
  tree. Exact imported payloads remain unchanged, including hexadecimal case, signed/zero-padded
  timestamps, folded/repeated unknown headers and both signature header names.
- `object_format()` on `Tree`, `Commit`, `Tag`, `LooseObjects`, `Object` and `Objects` exposes the
  selected format. Object identity hashes the appropriate format and exact retained bytes.
- `LooseObjects::new(directory, format)` and `Repository::loose_objects()` are now infallible handle
  constructors because both closed formats are supported. Reads reject foreign IDs before filesystem
  access. Structured writes reject foreign objects before directory creation or publication. Blob
  bytes are uninterpreted. Framing, size bounds, compression completion, duplicate validation and
  no-clobber publication retain their previous contracts.
- `Repository::init(format, path, kind)` creates SHA-1 version-0 or SHA-256 version-1 configuration
  with `extensions.objectFormat = sha256`. Open/discovery use the common configuration in ordinary,
  bare, separate-gitdir and linked layouts. Initialization still exclusively reserves metadata and
  refuses existing destinations without overwriting them.
- `Repository::objects` supports SHA-256 loose-only snapshots. History walks, ancestry, tree
  comparison and blob-content loading carry the store's format. Null/foreign inputs never become
  truncated SHA-1 IDs. Tree comparisons keep gitlinks opaque and retain their existing equal-ID skip
  and cancellation semantics.

All in-repository callers were migrated directly. No compatibility overload, format registry,
conversion layer, new runtime dependency or new public module was added. `TagError::ObjectFormat`
was removed because a tag has a single format-bearing target; parsing errors remain
`InvalidObjectId`. The obsolete loose `Error::UnsupportedFormat` variant was removed.
`ObjectReadError::Unsupported` and `index::StorageError::UnsupportedFormat` express the newly
reachable storage boundaries.

## Scoped Refusals and Ownership

Opening a SHA-256 repository does not imply support for every operation on it:

| Boundary                                                             | Current result                                                                                  | Owner                             |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | --------------------------------- |
| `.pack` or `.idx` in a SHA-256 object snapshot                       | Explicit unsupported error before interpreting artifacts; direct loose access remains usable    | R05                               |
| Files refs, packed refs and reflogs                                  | `Repository::references` refuses SHA-256, including symbolic-only operations                    | R05 widths; R11 semantics         |
| Index read/edit                                                      | Unsupported format before reads or lock creation; existing bytes/locks remain intact            | R05 widths; R12 versions          |
| Status/checkout                                                      | Remain SHA-1-only through index/ref boundaries; SHA-256 target IDs also fail checkout preflight | R05 and later owning capabilities |
| SHA-1 fetch pack installation                                        | SHA-256 destination refused before temporary files or publication, including empty transfers    | R05 storage; R26 negotiation      |
| Fetch local knowledge                                                | SHA-256 store refused before constructing SHA-1 negotiation state                               | R26                               |
| Push and transport                                                   | Existing SHA-1 identity/protocol refusals remain                                                | R29 negotiation                   |
| Unknown extensions, compatibility hash, alternates, shallow metadata | Existing explicit opening refusals remain                                                       | R10/R14 and discovered follow-ups |

Pure SHA-1 pack/index codecs still require their documented format; binary bytes have no reliable
format autodetection. R05 must propagate widths through trailers/checksums, delta base references,
pack IDs/index tables, refs/reflogs and working-tree index entries before removing these refusals.
Transport negotiation must remain explicit after R05; storage support alone cannot authorize it.

## Compatibility and Failure Evidence

`tests/sha256.rs` generates original disposable repositories and uses only the Git executable as an
oracle. It clears inherited Git overrides and disables system/global configuration and templates. No
upstream implementation or test source was consulted.

- Both hashes and both initialization kinds exercise blobs, empty/nonempty trees, all five entry
  modes, root/parent commits and annotated tags through public APIs. `hash-object`, `cat-file` and
  strict `fsck` independently verify girt output. Distinct Git-written objects are read by girt.
- Git-created separate-gitdir and linked layouts share the correct format and object directory.
  Git-generated SHA-256 packs are refused by snapshots while Git still passes strict fsck.
- Canonical fixtures pass `fsck --strict`. Negative timestamps and noncanonical signed/zero-padded
  timestamps are stored with `hash-object --literally`, then compared through `cat-file` and girt.
  Ordinary `hash-object` rejects the negative-date fixture with `badDate`; byte storage/readback is
  not decoded acceptance or fsck acceptance. Signature payload removal composes with R01's
  `CommitPayload`, retaining the unselected unknown header.
- Units cover both-format empty-tree literal hashes, truncated digests, foreign gitlinks/parents/
  tag targets, malformed hexadecimal IDs and foreign content under a valid loose-object hash.
  Construction/read refusal occurs before creating missing storage.
- Both-format loose units exercise exact/exhausted payload limits, duplicate validation, corrupt
  existing file preservation, failed publication cleanup and concurrent identical writers. Existing
  shared decoder tests retain framing, decompression and storage-failure coverage. Failed writes can
  leave created directories; power-loss durability and hostile path replacement remain excluded.
- Public traversal tests exercise foreign IDs, history bounds and tree cancellation. Loose I/O and
  history have no cancellation parameter; cancellation during a synchronous loose read is not
  promised. Tree/content operations retain their between-read checks.
- R03 spans retain hierarchy/ownership and completion classification. Loose read/write and snapshot
  open record only the closed object format. Tests check SHA-256 success, mixed-format write/index
  refusal, installation refusal before publication and absence of sensitive sentinels/events.

## R07 Follow-Ups

**Resolved by R07:** [Retained decoding and peeling evidence](r07.md) records the public APIs,
independent observations, tested revision and remaining integration/platform owners. The following
list records the requirements assigned at this earlier completion.

The existing [R01 interpretation follow-ups](r01.md#r07-follow-ups) remain required in both formats.
R04 does not broaden tree mode spelling, person/date grammar, known-header ordering or tag peeling.
Structural `CommitPayload` access must not be treated as equivalent to decoded `Commit` acceptance.
R07 must characterize historical modes, tolerant identities/dates, repeated/misordered known headers
and nested annotated-tag peeling, preserving the original bytes and distinguishing read acceptance
from strict validation. No finite corpus proves universal Git parity.
